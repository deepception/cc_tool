# Design & frontend taste (taste-skill + design-director + product-ui-motion)

Frontend visual work (landing pages, heroes, portfolios, redesigns) is covered by two layers. `install.sh` (or `cc-install-tasteskill`) installs taste-skill (MIT) as **global** skills. From [Leonxlnx/taste-skill](https://github.com/Leonxlnx/taste-skill) comes `design-taste-frontend` v2, a scripted art-direction run: it deals one of twenty researched directions, writes the copy deck, finds credited pictures in open collections, then gates the page with a real-browser inspector at three widths and a screenshot critique. The inspector needs Node 22+ and Chrome, and a full page run takes 30 to 45 minutes and a few hundred thousand tokens (a single component or section skips most of it). Since v2.1 it also has an app-screen route for dashboards and admin views, and its audit-first redesign mode replaces the old `redesign-existing-projects`. From [Leonxlnx/taste-skill-classics](https://github.com/Leonxlnx/taste-skill-classics) come three pre-v2 styles: `minimalist-ui`, `industrial-brutalist-ui` and `high-end-visual-design`. Upstream made them opt-in, so Claude cannot load them itself; you run `/minimalist-ui` and so on. `full-output-enforcement` is no longer installed: upstream removed it, and it contradicted the managed block's output discipline. `cc-update` migrates an older install (classics moved to their new repo, the two retired skills removed). The **`design-director` project skill** (copied by `cc-setup`) is the control layer: it reads the brief, routes to `design-taste-frontend` or names a classic for you to run, and, when the full taste-skill run is not used, composes a section-by-section *master design prompt* from three archetype templates (signature-interaction hero, immersive scroll experience, dark minimal landing, distilled from motionsites.ai-style briefs) plus a prompt-anatomy guide. Two neighbouring skills are run by you, not by Claude: `design-director` tells you to run `/scroll-world` for a scroll-scrubbed "fly through the world" page (it needs paid external services, and the skill sets `disable-model-invocation`), and `/design-an-interface` is the answer to module and API shape questions. Say "design a landing page for X" and the routing happens automatically; the archetypes also work standalone if taste-skill isn't installed. If Anthropic's `frontend-design` skill is installed too, it covers the same requests; `design-director` keeps it to one design method per page.

Those two layers cover the *marketing* surface. Screens inside an existing app follow the app's own component system; `design-taste-frontend`'s app-screen route is meant for a new app with no system yet. The **`product-ui-motion` project skill** owns what they leave behind: how product components actually move. It asks whether a thing should animate at all before asking how — a frequency gate where 100+/day interactions get no animation at all — then supplies the exact durations, easing curves, `transform-origin` and interruptibility rules, with gesture physics (velocity handoff, Apple's momentum projection, rubber-banding) in a second reference. It fires on "add a drawer", "this dropdown feels sluggish", and as dimension 9 of the frontend review (`/app-qa frontend`), so the same catalog governs the code that gets written and the review that reads it. The rule set is derived from [emilkowalski/skills](https://github.com/emilkowalski/skills) (MIT) — condensed from four overlapping skills into one, with seven technical claims corrected against current browser and library behaviour and two blanket bans narrowed to the frequency arguments underneath them. Where the classic taste skills prescribe landing-page motion values (`transition: all`, transitions on *all* interactive elements, a flat `ease-in-out` ban; v2 dropped all three), `product-ui-motion` supersedes them at product scale; those files are third-party and npx-managed, so cc_tool states precedence rather than patching them.
