# The commands in detail

- **`cc-setup`** — initialize a project the first time: `.claude/settings.json`, `.claude/hooks/`, `.claude/skills/`, `CLAUDE.md`. Safe to re-run; idempotent on the parts it manages. It does not manage `.mcp.json` — add an MCP server directly or with `claude mcp add` if a project needs one.
- **`cc-update-project`** — roll new cc_tool changes into an existing project: re-copies hooks, adds new skills *and refreshes unmodified existing ones*, merges new hooks into `settings.json`, additively merges new `deny`/`ask` entries, applies the commit-attribution policy, and replaces the marker-delimited methodology block in `CLAUDE.md` in place. Preserves existing permissions and all project-specific CLAUDE.md content; never clobbers local edits. Ends with a non-destructive template-drift check (lists template sections the project lacks). **Note:** project-specific CLAUDE.md *structure* (Overview, Codebase Map, Commands…) is seeded once from the template and is **not** auto-merged on update — only the managed methodology block is. Internally calls `cc-setup` + `cc-update-permissions`.
- **`route-nudge.py`** (a hook, installed by `cc-setup` and `cc-update-project`): when an Agent call names no `model`, it adds one line to the call's context: what the call will run on (`CLAUDE_CODE_SUBAGENT_MODEL`, the session model for `Explore` and `Plan`, or the agent type's own definition) and the managed block's rule, name `model` on every call: `sonnet` for a spec'd execution arm, `haiku` for a read-only locating or extracting arm, `opus` for judgment. When the session's effort (Claude Code puts it in the hook input) is above medium and the call names no `effort`, it adds that subagents inherit it and suggests `effort: "medium"` for execution and read-only arms. It is registered for `PreToolUse` with matcher `Agent|Task`, sends `additionalContext` only (no permission decision, so the call proceeds exactly as before), prints nothing for a call that names a model, exits 0 on any error, and costs about 3 ms of its own work. The Routing panel above shows whether it helped.
- **`cc-update`** — updates global plugins (Superpowers as `superpowers@claude-plugins-official`, replacing an older `superpowers@superpowers-dev` install so the skills never load twice; checks/installs `security-guidance` from `anthropics/claude-plugins-official`; installs or migrates the taste-skill design skills, removes retired ones, and runs `npx skills update -g`). Independent of any project.
- **`cc-dash`**: a local dashboard of how your agents actually work, across every project. It reads the Claude Code transcripts under `${CLAUDE_CONFIG_DIR:-~/.claude}/projects/` (main sessions, `subagents/` and workflow agents) plus each repo's `.git/cc_tool/activity.jsonl`, starts a server on `127.0.0.1:7878`, opens the browser on a one-time pairing link, and runs until Ctrl-C. It is an on-demand process, not a daemon, and it never writes to `~/.claude` or to a project.
  - **Pairing**: transcripts hold secrets and `127.0.0.1` is reachable by every local user, so the dashboard's data needs a per-launch secret. cc-dash prints `http://127.0.0.1:<port>/pair#code=<random>` to its terminal; the code works once, for 60 seconds. To open the browser it writes that link into a 0600 file in a 0700 directory and opens the file, so the code never shows in a process's arguments. The page takes the code from the URL fragment, removes it from the address bar, and trades it (one same-origin POST) for a token it keeps in `localStorage`, which is scoped to this exact port: another local server on another port cannot read it, and new tabs share it. Every `/api/*` request carries the token as `X-CC-Dash-Token`; no cookie is used, because browsers send a `127.0.0.1` cookie to every port. The page shell, scripts and styles carry no data and load without it. Press Enter in cc-dash's terminal for a new link (another browser, or the first expired). After a restart the old token is void and the page says "Pair this browser with cc-dash": open the new link and it recovers by itself. On Linux a browser run by your own user pairs itself (`POST /api/pair-local`, checked against the owner of the connecting socket in the kernel's socket table), so `ccdash` opens straight into the dashboard with no link and no code.
    - **Pairing is read-only.** Every token that pairing gives (the link or same-user pairing) can read every page and `GET` endpoint and change nothing. Your agents run as your user, so "same user" does not mean "you", and the log `ccdash` writes holds the pairing link, which an agent can read. Acting needs the control code (Control mode, below).
  - **Live**: two modes (`v` switches). **Agents** (default) lists every agent working now (main threads, subagents, workflow agents) as a tree per session: what it is doing (running a tool with a timer, thinking, waiting on its subagents, your turn, finished, failed, or "stalled?" when a pending call has gone quiet), its model (with its effort when the transcript records one or the spawn call asked for one), N calls/min (calls started in the last 60 s) with a 15-minute spark (failed calls in red, the running minute lighter, a per-minute tooltip), new tokens and the burn rate in $/min (new tokens per minute for an unpriced model, never counting cache reads), and errors, beside a feed of the newest 50 tool calls that pauses on hover. An agent that needs you (from the alerts hooks, or a pending question or plan in the transcript) is marked and its session sorts first. **Sessions** shows one card per session written in the last 10 minutes. Polls every 3 seconds, re-reads only appended bytes, and updates the page in place.
  - **Alerts**: when an agent needs you, a toast appears within about two seconds (project, which agent, what it wants, how long it has waited; click to open the session). A bell in the top bar (`a`) lists everything open, the tab title reads `(2) cc-dash`, and the favicon gets a dot. Desktop notifications are opt-in (a button in the drawer, since browsers need a click) and an optional soft chime is off by default; both are remembered in the browser. An alert closes on its own when the agent moves on: you answered, the permission was granted or denied, a new prompt arrived, the next tool ran, or the session ended. Sources: the `attention.py` hook, which projects get from `cc-setup`/`cc-update-project` and which appends to `${XDG_STATE_HOME:-~/.local/state}/cc_tool/attention.jsonl` (0700 directory, 0600 file, rotated at 5 MB); for projects without it, a pending AskUserQuestion or ExitPlanMode in the transcript, and Claude Code's session registry (`~/.claude/sessions/`) for a waiting permission prompt. `GET /api/alerts` serves the open set.
  - **Sessions**: every session in the window with project, branch, active time, models, turns, tool calls, subagents, tokens, estimated cost, errors and guard catches. Search with `/`, move with `j`/`k`, open with Enter. The project filter lists every project with its session count; worktrees fold under their repo (`→` or the chevron shows them, typing finds them). A worktree is a `.claude/worktrees/<name>` directory, a linked git worktree, or a checkout next to the repo named `<repo>-<suffix>`, even after it was deleted. The choice is kept in the URL (`#/sessions?p=<project>&wt=<worktree>`), so reload and back keep it.
  - **Session detail**: a timeline, newest first by default (an Oldest first toggle is remembered; new entries arrive on top without moving what you are reading, and a pill counts them) (prompts, replies and handed-back reports rendered as Markdown, grouped tool calls, failures and guard refusals highlighted, plus markers where the effort or the model changed), an Agents tab, tool usage, tokens and cost per model (input, output, cache reads, cache writes), and the guard decisions attributed to the session. The header shows the session's effort and "fast mode" when any reply was billed fast; the tiles show cost, New tokens, Context, Subagents (all levels, with the depth) and the share of cost spent in subagents.
    - **Tokens, one rule everywhere**: cost is the headline. "New tokens" is input + cache writes + output; cache reads (the context re-read on every call, priced at a fraction of input) are shown apart ("+20.1M re-read from cache (95% off)") and never added in. Context is the last call's input + cache read + cache write. Subagent transcripts mostly save a reply's usage at the start of its stream, so for a reply with no final usage record cc-dash counts and prices the output its visible content holds (about 4 characters a token); such totals read "≥" and their tooltip says how much is estimated. Hidden thinking cannot be seen, so it stays a floor.
    - **Agents tab**: the session's whole agent tree at any depth. A subagent links to the Agent call that spawned it (`toolUseId` in its `.meta.json`, wherever that call was made), a workflow run to the Workflow call that returned its run id (also from inside a subagent), and a transcript with no matching call to its `parentAgentId`, or else it is marked unlinked under the main thread; cycles and trees deeper than 24 levels are cut safely. An expandable table gives each agent's model, effort, status, own and with-subagents new tokens and cost, active and wall time, and opens its timeline. Charts: cost (or new tokens, or cache reads) by depth stacked by model, a model x effort matrix (agents and cost per cell; a solid dot when the effort was recorded or asked for, a hollow one when it is inferred), thinking tokens as a share of output per model and effort (only replies that saved a thinking count), an icicle of where the cost went (each row one level deeper, a block's width is it plus everything it spawned), and when each agent ran, nested under its parent. `GET /api/session/tree?id=` serves it.
    - **Effort**: read from the `api-request` records Claude Code 2.1.29x and later write (`params.output_config.effort`), else from the Agent call's `effort` input. Otherwise it is inferred and shown as a dashed chip: a subagent runs at its parent's recorded effort (every sample that recorded both agreed), else at its model's default (`medium` for Opus, Sonnet and Haiku 5.5); a model with no known default shows none. Overview's "Which model did the work" adds the recorded effort mix per model.
  - **Projects** (the third tab): **Overview** (`o`), **Plans** (`p`) and **Docs** (`d`) for one project, or Overview and Plans for all of them. The project picker is the page title and the three views are tabs under it; the project you pick stays picked as you move between them, is kept in each view's URL (`?p=<project>`) and is remembered, and the Projects tab returns to the last of the three you used. Docs always needs a project: with "All projects" it opens the project you read last.
  - **Overview**: cost per day by model, activity, which model did the work in main sessions versus subagents, top tools, subagent types that failed or did not finish, and where things went wrong. A **Routing** panel (below) shows who picked each subagent's model and effort. A **Projects** table lists every project in the window, sortable: sessions, active time, cost with a per-day trend, tokens, tool calls, error rate, subagents, Opus/Sonnet/Haiku share, guard catches and last active, with worktrees folded under each; a row opens its sessions. Picking a project recomputes every number and chart for it (`#/overview?p=<project>`).
  - **Routing** (a panel in Overview, scoped like the rest of the page; hidden when the window has no subagents): who picked each subagent's and workflow agent's model and effort, what that cost, and where it diverges from the managed block's Model routing. It reads `GET /api/routing?project=`, one object per scope, built from the transcripts already loaded.
    - **Panel**: four stats (cost of agents whose model nobody named, the share of Opus agent cost at xhigh or max, cost of re-sending expired context, cost of agents whose context passed 300K), a table of cost by work type and model (amber where routing diverges: execution on Opus, read-only work on Opus or on Sonnet under 100K context), Opus agent cost by effort, and the five flagged agents with the most to save, each opening its timeline (`#/s/<session>/a/<agent>`).
    - **Where the model came from**: `explicit` (the Agent call's `model`, or `meta.model`), `workflow` (the workflow's `agent()` options), `type` (the agent type's definition in `.claude/agents/` or `~/.claude/agents/` sets `model:`), or `default` (nothing named one; Claude Code picked). `default` is flagged whatever the work was. Effort is read from the replies themselves (the `effort` on each assistant record, else the latest `api-request`'s `output_config.effort`); it is "named" when the Agent call or its metadata carried an `effort`, and inherited otherwise, which shows as the dashed chip.
    - **Work type is a heuristic**, from the agent's description, its first message and its tool mix (did it edit files or run a changing shell command, did it run tests, did it spawn agents): judgment (reviews, planning, root-causing, anything ambiguous), spec'd execution (an edit run that starts with a spec verb or names a change), read-only mechanical (an Explore or locate/list/extract sweep that changes nothing). The rules are in `lib/cc_dash/routing.py`; a hand check of 15 agents found 12 right, 1 borderline and 2 wrong, in both directions. "If re-routed" re-prices the same tokens on the model the block names and is an estimate.
    - **Expired context**: a reply that wrote at least 50K tokens of cache, at least half its context, after the cache had expired (idle more than 5 minutes for a subagent, 1 hour for a main session). Its cost is that cache write. Big writes after a shorter gap are not counted. "Context over 300K" is the whole cost of agents whose context passed 300K; the replies sent at that size alone are in its tooltip.
  - **Docs viewer** (`d`, `#/docs?p=<project>&f=<path>`): read each project's Markdown and HTML without leaving the dashboard. The project is the Projects area's shared one (worktrees fold into their repo, and the docs come from its main checkout); the last file of each project is remembered and kept in the URL. The tree groups files the way cc_tool projects are laid out: **Vault** (`vault/`), **Plans & specs** (`docs/superpowers/**`), **Docs** (the rest of `docs/`), **Project root** (README, CHANGELOG, CLAUDE.md, AGENTS.md), **Skills** (`.claude/skills/`) and **Other** (collapsed), with **Recently changed** on top for what an agent just wrote. Dated files (plans, digests) sort newest first. The box at the top filters file names as you type and, from two characters, searches the contents of the project's docs (`/` focuses it, `j`/`k` move, Enter opens). An open document reloads in place within about 3 seconds of a change on disk, keeping your scroll position.
    - **Markdown** is rendered in the page by a built-in renderer (`web/markdown.js`, no libraries, no network): CommonMark blocks, GFM tables, task lists (read-only), strikethrough and bare links, YAML front matter as a small key/value header, Obsidian `[[note]]`, `[[note|alias]]`, `[[note#heading]]` and `![[image.png]]` resolved by file name within the project (unresolved ones are shown as missing), a sticky table of contents on wide screens, and "Linked from" (backlinks) under each note. Raw HTML inside Markdown is shown as text, never rendered. Links to other `.md`/`.html`/`.txt` files open in the viewer; `http(s)` and `mailto` links open in a new tab; `javascript:`, `data:` and every other scheme are dropped. Relative images are fetched with the pairing token; images on the network are not loaded.
    - **HTML** files never run in the dashboard's origin. They load in an `<iframe sandbox>` without `allow-same-origin` from a one-time `/docs-frame/<ticket>` URL whose response sets its own CSP (`default-src 'none'`, inline styles, images only from `data:`/`blob:`, the CSP `sandbox` directive), so the document is an opaque origin that cannot read the dashboard's token or call `/api`, even with scripts on. Scripts are off; "Allow scripts in this preview" turns them on for that file in this tab only (`allow-scripts`, still never `allow-same-origin`, still no network).
    - **What can be read**: only projects cc-dash resolved from your sessions (the browser sends a project name, never a path), and inside one only relative paths that resolve, after following symlinks, to a file inside the project root. Refused: `..`, absolute paths, NUL bytes, backslashes, symlinks that leave the project, dotfiles and dot-directories other than `.claude/skills/`, skipped folders (`.git`, `node_modules`, `.venv`, `dist`, `build`, `.next`, `__pycache__`, `.claude/worktrees`, ...), anything but `.md`, `.markdown`, `.html`, `.htm`, `.txt` (and common image types for images), anything bash-guard treats as secret material (`.env*`, `id_rsa*`, `*.pem`, `*.key`, `.npmrc`, `.ssh/`, ...), FIFOs and devices, and files over 2 MB (10 MB for images). Text that looks like a live credential (write-guard's patterns: private keys, cloud and API keys, tokens, JWTs) is shown as `[redacted: <kind>]`, also when it sits right next to `-`, `_`, `=` or a quote. Search reads at most 1,500 files and 24 MB per query and returns at most 200 matches (5 per file).
  - **Plans**: how far your agents got with each implementation plan. A tab of the Projects area (`p`, `#/plans?p=<project>`; a plan's page is `#/plan?p=<project>&f=<path>`), also reached from the Overview's **Active plans** panel and from a plan chip.
    - **What counts as a plan.** In the projects of your sessions in the window, and in their worktrees: every `docs/superpowers/plans/*.md` with `### Task N` headings or checkboxes (the Superpowers writing-plans format), other `docs/**/*.md` with at least three checkboxes, `TASKS.md` and `docs/start-here.md`. Tasks are `Task N` headings at any level (ids like `7`, `A1`, `10b`); without them, each heading that owns checkboxes is a task. Steps are `- [ ]`/`- [x]` lines, never inside code fences. Milestones are the headings above the tasks (`## Phase 1`, ...) when there are two or more. The same path in several worktrees is one plan, and the most ticked copy wins. Files over 2 MB and symlinks are skipped.
    - **Where progress comes from.** Steps come only from the plan's checkboxes. A task is done when all its checkboxes are ticked, else when the subagent-driven-development ledger (`.superpowers/sdd/<plan>/progress.md`) says `Task N: complete`, else (no checkboxes) when its todo item is completed, else (a plan nobody ticks and no ledger) when its last implementer subagent finished. Each plan says which source its numbers came from. A plan with no tasks and no checkboxes shows its executing session's todo list instead.
    - **Who did what, and when.** A session executes a plan when it ticks it (an Edit flipping `- [ ]` to `- [x]`, or a `sed -i`/script naming it), writes its ledger, spawns `Task N` subagents for it ("Implement Task 3: ...", "Review Task 3 ..."), or keeps a todo list naming its tasks. Each task shows when it started (its first subagent, tick or todo update), when it finished (the tick of its last step, else the ledger write, else its agents' end), the subagents that ran it with model and outcome (each links to its timeline), and its commits (the ledger's `a..b` range, else commits made during its agents' runs; `git log`, read-only).
    - **Status**, in the same words as Live: Working (an executing session wrote in the last 10 minutes), Idle (it wrote within 2 hours), Needs a decision or Your turn (the executing session or one of its agents waits on you; the card links to the decision), Paused (unfinished, quiet for 2 hours), Not started, Done. A task's time is working time: its agents' active time with pauses over 30 minutes left out (the rule Sessions uses), so a subagent resumed hours later does not count its idle hours; a task timed only by a wall clock that holds such a pause says "with pauses". The median task time and an estimate of the work left appear once two tasks have a time, labelled as an estimate.
    - **Pages.** Progress always reads "13 of 14 tasks done · 91% of steps", with the current task on its own line: "Working on" while an agent runs it, else "Next up", or "First open task" when later tasks were finished out of order. Plans in progress lead as cards (status, one progress bar split into milestones and filled by steps done, the current task and who is on it with a timer, started, and the estimate); paused plans follow in a compact list, and not started and done plans fold into their own lists. Plans with no activity in the window are behind "Show older plans". A plan's page adds the task list (expand a task for its steps with tick times, agents and commits), tasks done over time, the sessions that executed or read it, and links to open the plan (Docs view) and the session. Live rows and session headers carry a compact "Plan · 4 of 9 done" chip for the session driving a plan. `GET /api/plans?project=[&all=1]` and `/api/plans/detail?project=&path=` serve it; the path must be a discovered plan inside that project's checkouts.
  - **Control mode** (`cc-dash --control`; off by default): act on your agents from the dashboard instead of switching terminals. Needs the `dash-control.py` hook, which projects get from `cc-setup`/`cc-update-project`; it does nothing at all unless a `cc-dash --control` is running (it checks a lease file cc-dash refreshes every 2 seconds, behind a shell `test -e` that costs about 1.5 ms per event with no dashboard).
    - **What it can do.** Approve or deny a permission prompt (deny with a reason Claude reads), answer an AskUserQuestion (options, multi-select, free-text "Other"), approve a plan or reject it with feedback (Claude revises and resubmits), "Allow for this session" (Claude Code's own suggested rule, added for this session only, never written to a settings file), send a message to a session or a subagent, and "Stop at next tool call" (denies the next tool call and ends the turn; a tool that is already running finishes first). Cards appear in the toast, the alert drawer, and at the top of the session or subagent page. Live rows get a Review button (Answer for a question, Review plan for a plan) beside a "Needs a decision" badge, plus a Message button; Review opens the session page with the full card. A row never approves or denies: its text is a one-line summary, and a decision is only ever made on the card. `y`/`n` (pressed twice) act on a focused card, `m` opens the message box.
    - **The terminal stays live.** The prompt opens in the terminal at the same moment and the first answer wins. Answer in the terminal and the dashboard card says "Answered in the terminal" within about a second (the hook watches attention.py's log and the session registry; cc-dash also polls `claude agents --json`). A waiting hook gives up after `--control-wait` seconds (default 300) or as soon as cc-dash stops, and the prompt simply stays in the terminal.
    - **Messages.** To a session's main thread they go over the session's inbox socket (Claude Code's cross-session messaging): an idle session starts a turn at once, a busy one reads it after the running tool. Claude sees it as a message from another session, not a prompt you typed, and a session in bypass mode holds it for approval (5 minutes); `--bare` sessions have no socket. Without a reachable socket, and always for subagents, the message waits for the hook: after the agent's next tool call, at the end of its turn, or with your next prompt. Each message shows Queued, Delivered (and how) and Seen (the agent wrote after delivery).
    - **The control code.** With `--control`, cc-dash makes a per-launch code such as `7K4M-QX2P-9HTW` (three groups of four from an alphabet without 0/O/1/I/L, about 59 bits) and writes it to its own terminal (`/dev/tty`) and nowhere else: not to stdout or stderr (often the log), not to any file or the state directory, not into argv or the environment. The dashboard opens read-only: decision cards, the message composer and Stop show "Enter the control code from your terminal to act" in place of their buttons. Type the code once; the page trades it (`POST /api/control/unlock`) for a control token it keeps in the tab's memory only, because `localStorage` and `sessionStorage` are files in the browser profile that anything running as you can read. A reload asks for the code again; the code works for this launch and never after it. Codes are compared in constant time, and each tab has its own small budget: one try a second, and after 5 wrong codes that tab is locked ("Too many wrong codes from this tab. Reload the page to try again"). Nothing is shared between tabs, so another tab (an agent's pair-local token, say) can neither lock you out nor use up your tries: the right code from a tab with budget left is always accepted at once. Fresh tabs cost nothing: same-user pairing is not rate-limited (a cap would let an agent lock your browser out), so an agent minting tokens gets 5 tries from each, and the code's ~59 bits put guessing far beyond any launch's life even at thousands of tokens a second. The code goes into the unlock field and nowhere else: a deny reason, an answer or a message that contains it (in any case, with any spacing or separators) is refused with "That text contains your control code", so a card or message that asks for the code gets nothing, and the code is never written to a decision file or the audit log. `cc-dash --control` refuses to start without a terminal (a service, a pipe), while another `cc-dash --control` holds a live lease (stop that one first; `ccdash --control` does; a lease counts only when its pid passes the same program check the hook applies, below, and any other lease is removed with a note on the terminal), and from inside a Claude Code session: "cc-dash --control must be started from your own terminal, not from inside a Claude Code session". That last check runs in cc-dash itself, so it does not depend on parsing any command: it looks for the variables Claude Code sets for its Bash tool's processes (`CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_CODE_SESSION_ID`, `CLAUDE_PID`, `CLAUDE_CODE_EXECPATH`, `CLAUDE_CODE_CHILD_SESSION`; checked with `env` from a headless `claude -p` Bash call) walks its parent processes up to init for the claude CLI (the native binary, or node running it), does the same from its session leader and process-group leader (both outlive a double fork; a leader that is gone, hidden or in another pid namespace, or a parent chain that cannot be read to the end, counts as started inside Claude Code, since nobody can tell), refuses when a terminal driver (`script`, `expect`, `unbuffer`, `empty`, `socat`, `ttyrec`, `dtach`, `abduco`) among those processes was itself re-parented to init or a subreaper, refuses unless every process holding the master side of its terminal runs one of your recorded terminal programs (or inherited the fd from one that does), and refuses when such a holder is, or descends from, the claude CLI, or carries one of the variables above (whoever holds the master reads the control code: it finds `/dev/pts/<n>` from its own `tty_nr`, then the processes with a `/dev/ptmx` fd whose `/proc/<p>/fdinfo` says `tty-index: <n>`, and compares each one's `/proc/<p>/exe` with the terminal hosts `cc-setup` recorded; an agent's `pty.spawn` host is not one of your terminals, and an agent-started `tmux new -d` inherits those variables; nobody visible holding the master, a holder whose parents or environment cannot be read, or a hidden process descending from Claude Code (a process of yours, by its `/proc/<pid>/status` uids, whose fd table or fdinfo cannot be read, since any program can make itself non-dumpable, and whose parents or session or process-group leaders' parents include the claude CLI, read from `/proc/<pid>/stat`, which stays readable) counts too, because it could hold the master; a hidden process of yours outside Claude Code's lineage (an `ssh-agent`, an editor's sandbox helper) is not counted, the same-user limit below, so over SSH, where the sshd process holding the master is usually not dumpable and cannot be inspected, control mode does not start; every holder counts, so a program that leaks its master into a Claude Code process it starts later makes the dashboard refused too), and refuses a process that leads a fresh session after a re-parent, or was re-parented with no controlling terminal left. The hook applies exactly these checks to the dashboard from outside (below). `ccdash` starts cc-dash in a pipeline whose process-group leader, a subshell, exits at once, so cc-dash with `--control` and no terminal on stdin, stdout or stderr moves into a process group of its own. Closing the terminal that started `cc-dash --control` ends its session leader, and with it the hook's trust: restart control mode from a new terminal. **Your terminals.** `cc-setup` and `cc-update-project` record, in `cc_dash_manifest.json` beside the hooks (`terminal_hosts`), the real path of each program holding the master side of the terminal they run in: gnome-terminal-server, konsole, kitty, alacritty, wezterm, Cursor's or VS Code's pty host, a tmux or screen server (a holder that only inherited the fd from another holder, such as a shell some terminals start with their other tabs' masters, is left out, and so are the holders' parents, which would be your shell and the user manager). Never recorded: a holder that is, descends from or carries the variables of Claude Code, whose parent chain cannot be read, that runs with debug or eval switches (below), or whose program is a generic interpreter or pty driver, by its name family (python, node, nodejs, deno, bun, perl, ruby, sh, bash, zsh, fish, dash and other shells, script, expect, unbuffer, socat, dtach, abduco) or by content (its sha256 equals that of an interpreter or shell on this system: python3*, python*, node, nodejs, deno, bun, perl, ruby, bash, sh, dash, zsh, fish, ksh, tclsh, expect, script, socat or unbuffer on PATH or in /usr/bin, /bin and /usr/local/bin; hashed once per process when sizes match, in memory only), so a renamed copy is caught too; tmux and screen stay recordable. The hook applies the content check to the terminal program holding the master as well (not to a shell that inherited the fd from it), so a recorded interpreter or a renamed copy is refused. And nothing at all is recorded unless cc-setup itself passes the same rules `cc-dash --control` starts by (one shared check, `origin_problem` in `cc_procs.py`): none of Claude Code's tool variables; no claude process among its parents or its session and process-group leaders' parents, and every one of those chains readable to the end (fail closed); no terminal driver (`script`, `expect` ...) on the way that was itself detached; neither it nor its session leader leading a fresh session after a re-parent; not re-parented with no terminal left; and a controlling pseudo-terminal of its own. Refused, it says why, records nothing (`CC_DASH_TERMINALS` included) and keeps the list. So an agent that runs `cc-update-project` through Bash on a terminal of its own making records nothing. Add more with `CC_DASH_TERMINALS=/path1:/path2 cc-update-project` (an interpreter named there is not recorded either), from a terminal that is recorded in the same run: with no recordable terminal detected, what it names is not recorded either; each run prints what is recorded and keeps what was recorded before, unless you pass `--reset-terminals`, which replaces the list with the terminal you run it from. Run without a terminal (piped, CI), it records nothing and says so: then run `cc-update-project` once from the terminal you will run `ccdash --control` in, or control mode refuses with "the terminal showing the control code is held by <program>, which is not one of your recorded terminals; run cc-update-project from your terminal to record it". A program from an AppImage (Cursor's) runs from a mount directory that changes every launch, so it is recorded by image name, path inside the image, size and full sha256, and matched only on a FUSE mount, never by its old mount path alone. Hashing its 200 MB binary takes about half a second, and the hash is kept in the hook process's memory only (keyed by the file's device, inode, size, mtime and ctime and by the mount, so any change rehashes), never in a file a Bash write could forge: a hook process lives for one event, so it hashes once per permission request, and repeated checks in it (each verify, the lease every second) reuse it; cc-dash hashes once at startup. Measured on Cursor's terminal here, per request: about 124 ms with the binary in the page cache (about 475 ms from disk). After an AppImage update, run `cc-update-project` again. A terminal program holding the master whose environment has `ELECTRON_RUN_AS_NODE`, `NODE_OPTIONS` or an `ELECTRON_*` debug or inspect variable, or whose argv has, bare or as `=value`, `-e`, `--eval`, `-p`, `--print`, `-r`, `--require`, `--import`, `--loader`, `--experimental-loader`, `--js-flags`, `-i`, `--interactive`, `--inspect*`, `--remote-debugging*`, any `--*-preload*`, or `--enable-logging=` with a file target, is refused and never recorded: told to run other code, it is not your terminal. (A terminal emulator started with `-e command`, as alacritty, kitty or konsole allow, is refused for that reason; start the command from its shell instead.) The environment variables count for every holder of the master, also one that inherited the fd from your terminal; the switches too, except for an inherited shell (bash, sh, dash, zsh, fish or ksh by content), where `-i` means interactive. cc-dash's union of the recorded terminals reads each project's manifest as the hook reads its own (no symlink followed, a plain file of yours that nobody else can write, under 1 MB); an unsafe one is skipped, noted on the terminal and in the audit log. cc-dash itself (it belongs to no single project) accepts the terminals recorded for any project in `projects.json`; each project's hook accepts only its own record. Its limit: an agent that launches one of your own recorded terminal or multiplexer programs (`tmux new -d` with Claude Code's variables scrubbed and double-forked away from it, say) hosts the code on a terminal that passes every check. That is the documented same-user limit; the record stops the generic ones (a few lines of Python with `pty`, `script`, `expect`). That is why the code still has to be typed by you, and why the guards still apply. The `ccdash` shell function prints the code above your prompt: cc-dash gets a pipe on fd 3 that carries nothing and closes it once the code is on the terminal, and the function waits for that. When control mode is refused (from inside Claude Code, on a terminal program that was not recorded, and so on), cc-dash writes the reason to that same terminal as well as to its log, and `ccdash --control` returns without saying the dashboard is opening.
    - **What stays final.** Deny rules and bash-guard refusals resolve before any permission prompt, so they never reach the dashboard. A command bash-guard asks about (the hook runs bash-guard's own checks on the command itself, so there is no marker file to delete or forge), or one matching a `permissions.ask` rule, shows the reason and needs `approve` typed, never a click, and never gets "Allow for this session". The card shows the whole request: every field of the tool input (a Write's whole content, every edit of a MultiEdit with its old and new text, a NotebookEdit's source, a Bash timeout or sandbox flag, an MCP tool's arguments), behind "Show all" when it is long (also in a toast), plus the session, agent, working directory, permission mode and MCP server. "Allow for this session" lists the exact rules it adds, and the hook applies it only when the rules it would add are exactly those. A request whose input was too long for the hook to pass whole (over 256 KB) offers only Deny and "Answer in the terminal": nothing approves what the card could not show. A decision applies only to the exact call it was made for (a sha256 of tool and input), commands are never edited, there is no "approve all", and approvals are rate-limited (6 per 10 s). Invisible and direction-changing characters in a command are shown as `⟨U+…⟩`, and the card always names the agent and working directory.
    - **Security.** Every write needs the control token, and is a POST with `Content-Type: application/json`, an `Origin` equal to the dashboard's own and, when the browser sends it, `Sec-Fetch-Site: same-origin`, plus the Host check. Hook and dashboard talk through files in `${XDG_STATE_HOME:-~/.local/state}/cc_tool/control/` (directory 0700, files 0600, no symlinks followed, written by atomic rename), but a file is only a doorbell: before it acts on a decision, a message or a stop, the hook asks cc-dash (`GET /api/control/verify` over cc-dash's hook socket, sent with a per-launch key from the 0600 lease) and applies cc-dash's own record of what a control-unlocked page sent in this launch, never the file's content. The hook and cc-dash talk only over that hook socket, never TCP (the TCP port is the browser's): `hook.sock`, a Unix socket cc-dash makes itself in its 0700 control directory (bound under a fresh random name, 0600, renamed over whatever was at the path, removed when cc-dash exits) and names in the lease. The hook connects only when the lease names exactly `<control dir>/hook.sock` and it is a 0600 socket of yours in that private directory, and believes the answer only when the kernel says the process listening is the lease's pid and your user (`SO_PEERCRED`; `LOCAL_PEERPID` on macOS) and the answer carries an HMAC under the lease key of a nonce the hook made for this exchange (`X-CC-Dash-Proof`), so a socket something else puts at that path cannot answer for cc-dash. cc-dash answers only a caller with the lease key that the kernel says runs as your user; a query never uses a record up, records expire by age, and a message or stop already delivered is not confirmed again. A decision is also bound to a digest of every field its card shows (tool, the whole input, session, agent, working directory, permission mode, flags, the session rules, the MCP server; the card and the digest list are checked to be the same set), so an approval applies only to the very request its card showed. A planted file, without a matching record, does nothing: the prompt stays in the terminal, and the dashboard's Control history shows "Ignored a forged file". A permission request does not travel through a file at all: the hook hands it to cc-dash directly (`POST /api/control/request` over the hook socket, with the lease key), and cc-dash shows only content received that way, bound to the hook's pid: the process that connected, as the kernel recorded it when the connection was made (`SO_PEERCRED`, so nothing scanned afterwards can race it), must be the very pid the request names, the client end of the connection must be held by that process alone (the kernel names the peer socket, `sock_diag` `UNIX_DIAG_PEER`, then one scan of every `/proc/<pid>/fd`; a hidden process descending from Claude Code, as above, also refuses), it must still be the same process after the checks (`SO_PEERPIDFD`, Linux 6.5 and later, so a pid reused after the hook exits does not count), and be a `dash-control.py` hook from this cc_tool checkout (`/proc/<pid>/exe` a Python interpreter running exactly `<project>/.claude/hooks/dash-control.py`, where `<project>` is the `CLAUDE_PROJECT_DIR` Claude Code put in that process's environment, whose `cc_tool_root` names this checkout, whose project `cc-setup` registered in `${XDG_STATE_HOME:-~/.local/state}/cc_tool/projects.json` (0600; an extra layer against planted cards, which carry no authority anyway: write-guard keeps the file tools off it, but Bash can still edit it)). Then the hook writes `req/<id>.json`, a doorbell that holds only the id: the card stays while it exists, but its content is never read, so rewriting it while the hook waits changes nothing shown. If cc-dash cannot be reached or does not take the request, the hook exits silently and the prompt stays in the terminal, as with no dashboard. A doorbell with no request behind it, or a request handed over from anything but a hook, is never shown, and the audit log records it.
    - **Which dashboard the hook trusts.** The lease is a file anything running as you can write, so the hook trusts its pid only when that process is the real cc-dash. `cc-setup` (and `cc-update-project`) records this checkout's real path in `.claude/hooks/cc_tool_root` (0600, beside the hooks; `.claude/` is a protected path in Claude Code, so an agent cannot rewrite it, or the hooks themselves, without your approval). `cc-setup` also records the interpreter cc-dash runs on: the python3 its own helper runs as (`python3 -`, found on PATH the way `bin/cc-dash`'s `#!/usr/bin/env python3` finds it, taken from the kernel's `/proc/self/exe`), its real path and sha256 in `cc_dash_manifest.json`. `bin/cc-dash` re-executes itself with the interpreter already running it (the one its shebang resolved, by `/proc/self/exe`), never one named in a file or a variable (anything running as you could write those and pick what your own terminal runs), as `<interpreter> -I <real path of bin/cc-dash>` with no `PYTHON*` or `LD_*` variables, so no `PYTHONPATH`, `PYTHONSTARTUP`, user site directory (`usercustomize`, `.pth` files), current directory or preloaded library can put other code into the dashboard (Cursor's AppImage terminal exports `LD_LIBRARY_PATH`; it is dropped too). When it reads the lease, and again before each verify, the hook checks the lease's pid from outside, with `cc_procs.py`, which `cc-setup` copies beside the hooks (the same file cc-dash runs on itself; the hook never runs code from the checkout, which lies outside the project where an agent can edit it): `/proc/<pid>/exe` is the recorded interpreter: the same real path, and the file the kernel runs (`/proc/<pid>/exe` opened, so a binary replaced since does not count) has the recorded sha256 (cached per process by inode, size, mtime and ctime; hashing an 8 MB interpreter takes about 15 ms once per hook process), so a binary merely named `python3` is not enough; its argv is exactly `<that interpreter> -I <pinned checkout>/bin/cc-dash`, nothing before the script (cc-dash's own flags may follow); `/proc/<pid>/environ` carries none of Claude Code's variables and no `PYTHON*` or `LD_*` variable; no `claude` process is among its parents or its session and process-group leaders' parents, and each of those leaders can be inspected (fail closed); no terminal driver on the way was itself detached; nothing that holds the master side of its terminal is Claude Code (below); it does not lead a fresh session after being re-parented; and it was not re-parented with no controlling terminal left. After a python3 upgrade (the same path, new contents) or a change of the python3 on PATH, the hook refuses the dashboard ("... not the one cc-setup recorded (its sha256 differs; run cc-update-project if python3 was upgraded, then restart cc-dash)"); cc-dash --control warns on its terminal when it was not started the way it starts itself. And its code must be the code `cc-setup` recorded: `cc-setup` writes `.claude/hooks/cc_dash_manifest.json` (0600) with the sha256 of `bin/cc-dash`, `templates/hooks/cc_procs.py` and every file under `lib/`, and the full list of directories under `lib/`; the hook recomputes it under the pinned checkout (cached per process by size, mtime, ctime and inode; about 1 to 2 ms in a fresh hook process) and refuses on any difference, a missing entry, an unlisted file or directory of any name or kind (a `lib/json.py`, an extension module), or a symlink or special file anywhere in that scope (judged with lstat): "cc-dash's code changed since cc-setup ran; run cc-update-project to re-record it if you changed it yourself". `bin/cc-dash` loads its package by path and never puts `lib/` on `sys.path`, and reads no `__pycache__` (those directories are left out of the record), so neither a stray module nor a planted `.pyc` can stand in for recorded code. Matching hashes alone do not prove the running process loaded that code (it could have been started from changed files that were then put back), so the hook also requires every file and directory in that scope, and the record itself, to have last changed (ctime, from lstat, which any write, rename or restore sets and a normal user cannot set back) at least a second before the dashboard process started (its start time from `/proc/stat` btime and `/proc/<pid>/stat`, both rounded down, so the estimate is never late): otherwise "cc-dash's code changed after the dashboard started; restart it". A dashboard started within a second or two of a code change or of `cc-update-project` is therefore refused; restart it. `cc-setup` leaves the record untouched when nothing changed. A Bash edit of the checkout therefore makes the hook stop trusting the dashboard (prompts stay in the terminal) rather than vouch for itself. After a `git pull` of cc_tool, run `cc-update-project` in each project, as for any upgrade, to re-record it. So a copy of cc_tool, or a fake checkout an agent starts as `python3 …/bin/cc-dash`, is not trusted however it answers. After updating cc_tool, run `cc-update-project` in each project so the hooks and the pin match; until then the hook trusts no dashboard and prompts stay in the terminal. While cc-dash runs, a lease written over its own is put back and audited.
    - **Ask rules beyond Bash.** `permissions.ask` rules for Bash are matched with bash-guard's own shell parser (env prefixes, wrappers, subshells, `sh -c`, xargs). Other tools follow the documented forms: `Read(...)`/`Edit(...)` paths with gitignore semantics (`//abs`, `~/home`, `/` from the settings file's own anchor, `path` or `./path` from the working directory, `*` within a segment, `**` across, a bare name at any depth, a one-directory `dir/**` at any depth), Edit rules covering Write, MultiEdit and NotebookEdit and Read rules covering Grep and Glob, `WebFetch(domain:...)` with `*.` and in-label wildcards, `mcp__server` / `mcp__server__*` / tool-name globs, `Agent(Name)`, `Skill(name)` and `Tool(param:value)`. A rule that names the tool in a form cc-dash cannot check (an unknown specifier, an unclosed `[`, `~user`, a `/path` rule from managed settings, a search whose directory a path rule may reach, a call without the path to compare) reads "(not checked: ...)" and is treated as matching, so it needs the typed `approve`, as does anything bash-guard cannot parse and an unreadable settings file.
    - **What the guards add, and their limit.** write-guard refuses Write, Edit, MultiEdit and NotebookEdit into `${XDG_STATE_HOME:-~/.local/state}/cc_tool/control/` and into `cc-dash.log`, into the project registry `projects.json`, and anywhere in the pinned cc_tool checkout (the code cc-dash and the hooks run), judged on the real path (symlinks resolved) of every path field the call carries (`file_path`, `path`, `notebook_path`; a decoy field cannot stand in for the real one). A session in the cc_tool checkout itself, or in one of its git worktrees, may edit it: developing cc_tool is outside control mode's protection, so review those changes as you would any change to a tool you run. bash-guard does not match those paths, or the dashboard's endpoints, in command text: that can never be complete (bash builds paths at run time), and the hook does not depend on it, since it acts only on cc-dash's own in-memory records, checks the dashboard process itself, and binds every decision to what its card showed. bash-guard refuses (BLOCKED) a Bash command that starts `cc-dash`/`ccdash` with `--control` (also `--control=…` and any `--c…` prefix; cc-dash itself rejects abbreviations), including inside `sh -c`, `script -c`, `eval`, here-strings, heredocs, text piped into a shell or xargs, `setsid`/`nohup`/`env`/`sudo`/`timeout` wrappers, `python3 …/bin/cc-dash`, `python3 -m cc_dash.server`, inline code that imports `cc_dash.server`, `cc_dash.auth` or `cc_dash.control`, and `runpy` on cc-dash (reading transcripts with `cc_dash.store` stays allowed). It asks (NEEDS APPROVAL) when cc-dash's arguments contain anything the shell expands at run time (`$VAR`, `$(…)`, backticks, globs, braces): name and flag matching is not a boundary, which is why cc-dash checks for Claude Code itself. Reading transcripts, `attention.jsonl` and `GET /api/live` (or any other read endpoint) from a script stays allowed. A launch-time confirmation was considered and left out: anything typed into or clicked on a terminal or desktop session can be scripted by a program running as you.
    - **Threat model.** What holds: an agent acting through the tool calls the hooks see (Bash, Write, Edit, MultiEdit, NotebookEdit) cannot approve its own prompt, message a session as you or stop one. Pairing gives it read-only access at most; acting needs the code that only your terminal showed, and text carrying that code is refused; every decision, message and stop is confirmed with the running dashboard's memory, not taken from a file; the hook believes only the pinned checkout's cc-dash, launched from outside Claude Code, so a lease pointing at the agent's own server or a copy of cc_tool is ignored; a request card comes only from a real hook process; every decision is bound to the whole card, which shows the whole request; and write-guard and bash-guard refuse the plain routes to the control directory and to a second control-mode dashboard. These layers back each other up; none of them is a sandbox. What does not hold, because it runs with all of your rights: a deliberately evasive process running as your user. It could detach from Claude Code, scrub its environment and drive a pseudo-terminal to start its own `cc-dash --control`; overwrite its own argv and environment in memory so the process check reads clean; write into the pinned cc_tool checkout through Bash (write-guard covers only the file tools and bash-guard does not match paths in command text; the code record makes the hook refuse the changed dashboard, but a change to anything else in the checkout, or one you then re-record with `cc-update-project` without reading it, is not caught), or, in a session opened in the cc_tool repository itself, through any tool (its edits run the next time you start cc-dash: review them like any change to a tool you run); add a directory to `projects.json` through Bash and run a copy of the hook there with a made-up `CLAUDE_PROJECT_DIR` (that card has no real permission prompt behind it: approving it only answers the agent's own process, and the code can never be typed into it); read or drive the terminal that shows the control code (a terminal multiplexer's scrollback or `send-keys`, say: control mode trusts that terminal and has no out-of-band confirmation); run the real hook by hand with an invented request, as its own process, so it is the connecting process and the sole holder of its socket (the card is real, but no real permission prompt sits behind it: nothing waits on its answer, and the code cannot be typed into it); fake a hook's handover from a process that is not Python but is named like it and runs the hook's path (the hook process is judged by its script path, its interpreter only by name, since Claude Code may run hooks with any python3: the card it gets shown has no real prompt behind it and cannot be approved into one); hide a process of its own from the terminal and socket scans by making it non-dumpable (`prctl(PR_SET_DUMPABLE, 0)`) after double-forking it away from Claude Code (one under Claude Code refuses control mode while it runs); start `cc-dash --control` as a user service (`systemd-run --user`, a launch agent), or under one of your own recorded terminal or multiplexer programs (`tmux new -d`, say) after scrubbing Claude Code's variables and double-forking away from Claude Code (the recorded-terminal check stops a generic pseudo-terminal host, not your own programs); run `cc-update-project` from a terminal program of its own that it double-forked away from Claude Code, with a scrubbed environment, on a pseudo-terminal it made (the recording gate applies the same rules as `cc-dash --control`, so it refuses Claude Code's variables, a claude process among the parents or the session and process-group leaders' parents, a detached `script` or `expect`, a fresh session after a re-parent and no terminal at all, and a generic interpreter or driver is never recorded, but a compiled terminal program with a clean lineage looks like yours);  attach to the dashboard or the hook with ptrace, or rewrite their memory, which the process checks cannot see; or keep overwriting the lease so control mode stops working (cc-dash puts its lease back and audits it). Out-of-band confirmation of each approval (on another device, say), refusing user-service launches outright, and blocking ptrace or memory rewriting are not built: each needs something that does not run as you, and the same-user limit is documented instead. No mechanism that also runs as you can stop such a program; it could just as well rewrite your settings' allow rules or your shell profile. Without `/proc` (macOS) the process checks cannot run, and the dashboard's keyed, socket-checked answer is the anchor. For an agent you do not trust, use the devcontainer (`cc-devcontainer`).
    - **Audit.** Every dashboard action and its result (approved, denied, answered, message, stop; applied, answered in the terminal, delivered) is appended to `control/audit.jsonl` (0600) with the time, the launch id, the client, the target session and agent, and the text. Each session and subagent page shows its "Control history".
  - Flags: `--port N` (default 7878; a free port is used if it is taken), `--no-open`, `--days N` (lookback, default 7), `--project <text>` (only sessions whose working directory contains it), `--control`, `--control-wait SECS` (5 to 590, default 300). Cost is an estimate from token counts and the price table in `lib/cc_dash/pricing.py`; a model missing from it shows tokens with cost n/a. The server answers only to `Host: 127.0.0.1:<port>` or `localhost:<port>`, serves a fixed set of files, and loads nothing from the network.

`cc_tool` itself is local-only — edit templates in place, then run `cc-update-project` on any project to pick up changes.

> **Config staleness:** re-audit your hooks, permissions, and CLAUDE.md roughly once per Claude model release. Capabilities and failure modes shift between models — a guardrail that earned its keep on one model may be noise (or a gap) on the next — and a release may add a *new active tier* (a second model worth routing specific work to) or make instructions written for an older model too prescriptive for the newer one while remaining appropriate for the older one. Re-auditing covers all three: stale guardrails, model routing, and over-scaffolded guidance. Two tools do it: the shipped [`model-recalibration-audit.js`](../../.claude/workflows/model-recalibration-audit.js) workflow for the whole setup, and the bundled `/claude-api prompt-audit` command for the prompt text itself (CLAUDE.md, skills, workflow prompts) — v0.0.16 was produced by the latter.
