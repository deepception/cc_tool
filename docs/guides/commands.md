# The commands in detail

- **`cc-setup`** — initialize a project the first time: `.claude/settings.json`, `.claude/hooks/`, `.claude/skills/`, `CLAUDE.md`. Safe to re-run; idempotent on the parts it manages. It does not manage `.mcp.json` — add an MCP server directly or with `claude mcp add` if a project needs one.
- **`cc-update-project`** — roll new cc_tool changes into an existing project: re-copies hooks, adds new skills *and refreshes unmodified existing ones*, merges new hooks into `settings.json`, additively merges new `deny`/`ask` entries, applies the commit-attribution policy, and replaces the marker-delimited methodology block in `CLAUDE.md` in place. Preserves existing permissions and all project-specific CLAUDE.md content; never clobbers local edits. Ends with a non-destructive template-drift check (lists template sections the project lacks). **Note:** project-specific CLAUDE.md *structure* (Overview, Codebase Map, Commands…) is seeded once from the template and is **not** auto-merged on update — only the managed methodology block is. Internally calls `cc-setup` + `cc-update-permissions`.
- **`cc-update`** — updates global plugins (Superpowers as `superpowers@claude-plugins-official`, replacing an older `superpowers@superpowers-dev` install so the skills never load twice; checks/installs `security-guidance` from `anthropics/claude-plugins-official`; installs or migrates the taste-skill design skills, removes retired ones, and runs `npx skills update -g`). Independent of any project.
- **`cc-dash`**: a local dashboard of how your agents actually work, across every project. It reads the Claude Code transcripts under `${CLAUDE_CONFIG_DIR:-~/.claude}/projects/` (main sessions, `subagents/` and workflow agents) plus each repo's `.git/cc_tool/activity.jsonl`, starts a server on `127.0.0.1:7878`, opens the browser, and runs until Ctrl-C. It is an on-demand process, not a daemon, and it never writes to `~/.claude` or to a project.
  - **Live**: two modes (`v` switches). **Agents** (default) lists every agent working now (main threads, subagents, workflow agents) as a tree per session: what it is doing (running a tool with a timer, thinking, waiting on its subagents, your turn, finished, failed, or "stalled?" when a pending call has gone quiet), its model, tool calls per minute over 15 minutes, tokens and burn rate, and errors, beside a feed of the newest 50 tool calls that pauses on hover. An agent that needs you (from the alerts hooks, or a pending question or plan in the transcript) is marked and its session sorts first. **Sessions** shows one card per session written in the last 10 minutes. Polls every 3 seconds, re-reads only appended bytes, and updates the page in place.
  - **Alerts**: when an agent needs you, a toast appears within about two seconds (project, which agent, what it wants, how long it has waited; click to open the session). A bell in the top bar (`a`) lists everything open, the tab title reads `(2) cc-dash`, and the favicon gets a dot. Desktop notifications are opt-in (a button in the drawer, since browsers need a click) and an optional soft chime is off by default; both are remembered in the browser. An alert closes on its own when the agent moves on: you answered, the permission was granted or denied, a new prompt arrived, the next tool ran, or the session ended. Sources: the `attention.py` hook, which projects get from `cc-setup`/`cc-update-project` and which appends to `${XDG_STATE_HOME:-~/.local/state}/cc_tool/attention.jsonl` (0700 directory, 0600 file, rotated at 5 MB); for projects without it, a pending AskUserQuestion or ExitPlanMode in the transcript, and Claude Code's session registry (`~/.claude/sessions/`) for a waiting permission prompt. `GET /api/alerts` serves the open set.
  - **Sessions**: every session in the window with project, branch, active time, models, turns, tool calls, subagents, tokens, estimated cost, errors and guard catches. Search with `/`, move with `j`/`k`, open with Enter. The project filter lists every project with its session count; worktrees fold under their repo (`→` or the chevron shows them, typing finds them). A worktree is a `.claude/worktrees/<name>` directory, a linked git worktree, or a checkout next to the repo named `<repo>-<suffix>`, even after it was deleted. The choice is kept in the URL (`#/sessions?p=<project>&wt=<worktree>`), so reload and back keep it.
  - **Session detail**: a timeline, newest first by default (an Oldest first toggle is remembered; new entries arrive on top without moving what you are reading, and a pill counts them) (prompts, replies, grouped tool calls, failures and guard refusals highlighted), when each subagent ran and what it cost, tool usage, tokens and cost per model (input, output, cache reads, cache writes), and the guard decisions attributed to the session.
  - **Overview**: cost per day by model, activity, which model did the work in main sessions versus subagents, top tools, subagent types that failed or did not finish, and where things went wrong. A **Projects** table lists every project in the window, sortable: sessions, active time, cost with a per-day trend, tokens, tool calls, error rate, subagents, Opus/Sonnet/Haiku share, guard catches and last active, with worktrees folded under each; a row opens its sessions. The **Scope** picker recomputes every number and chart for one project (`#/overview?p=<project>`).
  - Flags: `--port N` (default 7878; a free port is used if it is taken), `--no-open`, `--days N` (lookback, default 7), `--project <text>` (only sessions whose working directory contains it). Cost is an estimate from token counts and the price table in `lib/cc_dash/pricing.py`; a model missing from it shows tokens with cost n/a. The server answers only to `Host: 127.0.0.1:<port>` or `localhost:<port>`, serves a fixed set of files, and loads nothing from the network.

`cc_tool` itself is local-only — edit templates in place, then run `cc-update-project` on any project to pick up changes.

> **Config staleness:** re-audit your hooks, permissions, and CLAUDE.md roughly once per Claude model release. Capabilities and failure modes shift between models — a guardrail that earned its keep on one model may be noise (or a gap) on the next — and a release may add a *new active tier* (a second model worth routing specific work to) or make instructions written for an older model too prescriptive for the newer one while remaining appropriate for the older one. Re-auditing covers all three: stale guardrails, model routing, and over-scaffolded guidance. Two tools do it: the shipped [`model-recalibration-audit.js`](../../.claude/workflows/model-recalibration-audit.js) workflow for the whole setup, and the bundled `/claude-api prompt-audit` command for the prompt text itself (CLAUDE.md, skills, workflow prompts) — v0.0.16 was produced by the latter.
