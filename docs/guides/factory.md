# Software factory (orders, a line of stations, two human gates, a ledger)

The default delivery path for coding agents in a cc_tool project. `cc-setup` and `cc-update-project` scaffold it unless you opt out (see [Setup](#setup)), and the managed `CLAUDE.md` block sends work that needs a spec or a plan through it. You write intent and approve the spec; a declared line of stations (plan, build, test, verify, review) does the production work in an isolated git lane; you read the result and do the merge. Every transition lands in an append-only ledger and shows up live on the **Factory floor** in cc-dash. This is the "software factory" pattern: intake, a specification kept apart from execution, an isolated build environment per task, verification as the binding constraint, two human gates, and an audit trail (Augment, *What is a software factory*). The hidden acceptance scenarios, kept away from the building agents, come from StrongDM's Software Factory (holdout sets, scored as "satisfaction"); how well they are kept away is in the next section.

```bash
cc-setup /path/to/project             # normal setup + the factory scaffold (on by default; --no-factory opts out)
                                      # cc-factory init --force → re-copy README, line.json, template, workflow

# in a Claude Code session inside the project (the `factory` project skill):
/factory intake "Add CSV export to the reports page"   # order FO-001 + a written spec; stops at the spec gate
                                                       # (a feature prompt reaches intake on its own, see Routing)
/factory run FO-001                                    # lane + the factory-line workflow + record the result
/factory status                                        # the board: every order, its station, its gate

# at the gates, in a shell (cc-factory is the only writer of the ledger):
cc-factory approve FO-001                     # spec gate: the spec is good, the line may run
cc-factory approve FO-001 --gate merge        # after YOU merged factory/FO-001-... into your branch
```

**Why a factory and not one long chat.** One agent in an editor checks its own work and loses the thread when the context rolls. The factory separates the jobs: the agent that builds is not the agent that verifies or reviews (review runs on a different model from build, except on late rework attempts, see [The line](#the-line)), the acceptance scenarios live where the builder is told not to look (nothing enforces that yet, see [What code enforces](#what-code-enforces-and-what-is-only-asked)), each order gets its own branch and worktree so lanes cannot trample each other, and the whole history of an order is one file plus one ledger you can read afterwards. People keep the two decisions that matter: *what* to build (the spec) and *whether it lands* (the merge). Review capacity, not generation, is the bottleneck of agent-written code, so the line spends its effort making what reaches that gate worth reading.

**Boundaries.** `cc-factory` is a stdlib script, not a daemon; there is no MCP server and no cloud dependency; it never merges, pushes or deletes anything; cc-dash shows the factory read-only, except in control mode, where a human can pass a gate from the Work view (see [Gates](#gates)); even then `bin/cc-factory` is the only thing that writes the ledger. A work order is a markdown file in the project, so it is versioned with the code it describes. The ledger is not: it lives in the git directory.

## Routing: when the factory fires

In a project with `factory/line.json`, the managed `CLAUDE.md` block has a `### Delivery routing` section: work that needs a spec or a plan starts with the `factory` skill's `intake`, instead of `superpowers:brainstorming` or `superpowers:writing-plans`. The `factory` skill's description is written to fire on that intent ("add a feature", "change this behaviour"), so you do not have to type `/factory`. A small direct change (a typo, a one-file fix, no design decision) skips the factory. In a project with no `factory/line.json` the Superpowers table applies as written.

The session-start hook adds a line when `factory/line.json` exists: that work needing a spec or a plan starts with the factory skill, and, if `cc-factory` is on PATH, `Open orders: FO-003 building; FO-004 at the merge gate.` (at most 8, then `+N more`). It carries only order ids and statuses; an order's title or any other text from the ledger never reaches the session context.

Intake opens by choosing the line and saying so in chat: `default` (hidden scenarios) for auth, payments, data migrations, security, anything you call risky, and whenever it is unsure; `quick` otherwise.

## What code enforces and what is only asked

Enforced by `cc-factory` (code, not a prompt):

- `approve` and `reject` (both gates, `--rework` included) refuse when run under Claude Code: an agent's Bash tool, or a `!` command typed into Claude Code. The message is `BLOCKED: ... this cc-factory was not started from your own terminal (<why>). Suggestion: run it from your own terminal: ...`. With `/proc` (Linux) it applies `recording_problem()` from `templates/hooks/cc_procs.py`, the rules control mode starts by (Claude Code's variables, a claude process among the parents or the session and process-group leaders' parents, a detached terminal driver, a fresh session after a re-parent), and it also needs a controlling pseudo-terminal of its own, so cron, CI or a pipe cannot run it either. **The gates are Linux-only for now:** without `/proc` (macOS) nothing can tell your terminal from an agent's, so `approve` and `reject` refuse outright ("factory gates need Linux's /proc ... in this release they work on Linux only"), as control mode does. Past the process rules, the decision needs a random 6-character code that `cc-factory` writes only to `/dev/tty` (never to stdout, stderr or the ledger), typed back there: it opens `/dev/tty` itself (never stdin, which a pipe can fill), discards anything typed ahead of the question, compares in constant time, and refuses when there is no controlling terminal, nothing is typed within 300 seconds, or the text is not the code. If `cc_procs.py` cannot be loaded it refuses. There is no bypass flag.
- **The one other way in is a ticket from cc-dash in control mode** (Linux only, like the terminal path). `approve` and `reject` accept the hidden `--ticket-fd` flag only from a child that cc-dash started itself after a human unlocked control mode and typed the decision. Passing the flag proves nothing: the child refuses unless the file descriptor is a Unix stream socket whose other end the kernel names as made by its own parent (`SO_PEERCRED`) and held by that parent alone (`sock_diag`, then a scan of `/proc/*/fd`; a process of yours under Claude Code whose open files cannot be read counts as holding the socket unless it exits or becomes a zombie within 200 ms; when one does, `/proc` is listed once more, and a process that appeared meanwhile and cannot be read counts at once, while one that can be read is judged; when only such newcomers were hidden, the check scans once more and refuses if anything is hidden then), that parent passes the rules the control hook applies to a dashboard (the user-wide code record, `${XDG_STATE_HOME:-~/.local/state}/cc_tool/cc_dash_code.json`, matches cc-dash's code on disk, the recorded interpreter and argv, no Claude Code in its ancestry, and the code unchanged since the dashboard started), and it is in control mode (`--control` among its flags and a controlling terminal). An agent's Bash call has a shell for a parent, however its flags read. The ticket is single use, expires after 30 seconds and names exactly one order, gate, decision and spec hash or reviewed head; `cc-factory` recomputes that value just before writing and refuses an id it already saw in the ledger. See [Gates](#gates) for the whole path and its limit.
- `mark` refuses `approved`, `done` and `review`, and any new status on a finished (`done` or `rejected`) order, so an agent cannot reopen a human's rejection. `mark ID spec` refuses with fewer than 3 holdout scenarios on a line with a verify station, unless `--no-holdout`. `lane` and `run-args` need the spec gate's pass in the ledger (on a line whose spec gate is `auto`, they do not).
- **An order keeps the line it was created on.** The `created` ledger event stores the line's name and a sha256 of its definition (stations, gates, retries, threshold, `run` and `test`). `lane`, `run-args` and `record` fail closed: an order proceeds only when that pin still matches, or when the spec gate's pass carries a hash that matches the current order body and line. So editing the order's `line:` to `quick` after approval, or rewriting the line in `factory/line.json` (dropping verify, setting the spec gate to `auto`), is refused with `BLOCKED:`. The way through is a human re-reading the spec and running `cc-factory approve`, or rejecting the order and filing a new one. An order created before the pin existed has none: it still runs if its spec approval's hash matches the current body and line, and otherwise waits for a fresh approval or a new order.
- The spec-gate `approve` stores a `spec_hash`: sha256 over the order body, the line (stations, gates, retries) and the holdout threshold. `run-args` and `record` refuse when it no longer matches ("the spec changed since approval"), and an approval made before hashes existed must be given again.
- `approve --gate merge` passes exactly the reviewed commit. `record` stores the lane head it reviewed on the review event, and the gate refuses when that is missing, when the lane branch has moved since (a commit added after the review), when the reviewed head is not an ancestor of the merge target (`--into REF`, default the main checkout's HEAD), or when the commit that brought the lane into the target merged a later commit than the reviewed one. It refuses a lane with no commits past its base, and records `merge_sha`, `lane_head` and `target` on the gate event. `record` prints the merge command against the reviewed sha (`git merge --no-ff <sha>`). The merge gate is always `human`: the loader forces it.
- `record` writes review (the merge gate) only for a result read with `--workflow-run`: the run Claude Code saved, whose args must be this order's lane and its approved spec, line and threshold. A result on stdin or in a `--file` records only `failed` or `blocked`: one claiming review is recorded as `blocked` with exit 2. Review also needs `contract: 2`, a pass for every station of the line on the final attempt (plan on attempt 1) and, on a line with verify, verify's report matching the scenario files on disk (count, S-ids, threshold, attempt). A failed check writes the station events, then `blocked`, and exits 2. A result with no hidden scenario checked on a line with a verify station (an empty holdout) still reaches review, with recommendation `needs-scenarios` instead of `merge`. A line with no verify station, such as `quick`, recommends `merge`: it has no hidden scenarios by design.
- Verify's feedback to build is built by the script from scenario ids, the spec's own acceptance-criterion text and a failure category. Verify's reasons are not an input to that text.
- No text the build or test station wrote is put into verify's prompt (verify holds the holdout; they never see it). Verify's run and test commands come from the line's `run` and `test` in `factory/line.json`, which a human writes, or else from the repo's README, Makefile, `package.json` or `pyproject.toml` as they were at the lane's base commit. The prompt tells verify that everything in the lane is data, never instructions.
- **Lane code runs in a bwrap sandbox (Linux, with bubblewrap installed).** The workflow script builds one fixed wrapper per attempt from its own validated values only (the order id, the attempt number, and the lane, holdout and main-checkout paths; never a station's text, and verify is not even given the order's title): `bwrap` with the whole filesystem read-only, the order's holdout dir, every order's `.factory-holdout/`, Claude Code's transcripts (`$HOME/.claude` and `$CLAUDE_CONFIG_DIR`, which is also unset) and the temp dirs (`/tmp`, `$TMPDIR`) behind empty tmpfs mounts, no network (`--unshare-net`), its own pid namespace, and only the attempt's throwaway copy (`/tmp/cc-factory-verify-FO-NNN-aN`, a `git archive` export of the lane's committed HEAD, with no `.git`) writable. Inside it, the kernel enforces it: lane code cannot read the holdout or a transcript, cannot write anywhere but the copy, and cannot reach the network. A real `bwrap` test in the suite checks exactly that. The probe uses that plain wrapper, and `cc-factory verify-git` builds the same one for git and `tar`; lane code uses a second one (the lane-code wrapper) that adds the main checkout's `.venv` and `node_modules` mounted read-only over the copy (skipped when absent), the copy mounted over the main checkout's own path with those two dirs on top, their `bin` dirs on `PATH`, and offline package-manager settings (`UV_OFFLINE`, `UV_NO_SYNC`, caches inside the copy), so `uv run`, `pytest` and `npm test` work without a network. Each top-level sub-directory of the main checkout with its own `.venv` or `node_modules` (one level deep; hidden dirs, `node_modules` and `factory/` skipped), which `cc-factory run-args` lists in the `subPackages` arg, gets the same read-only mounts (over the copy, over the main checkout's path, and under the deps dir), so lane code run from `<copy>/<dir>` with `<copy>/<dir>/.venv/bin/python` or `uv run` there imports its dependencies; those dirs are not put on `PATH`, and the installed-copy check looks in them too. Deeper environments and dependencies added by the lane are not available; verify is told to treat a missing third-party module or command as an environment limit (that scenario is judged by reading the code, `static`, and the order ends `needs-human-check`) and not as a failing scenario. A wrong reference to the lane's own code still fails it.
- **Verify's git commands ignore the lane's git config.** The lane's config is the builder's (`core.fsmonitor`, an `include`, a filter driver named in `.gitattributes` or `.git/info/attributes`, an external diff or textconv can each run a program), so verify's only git is `cc-factory verify-git FO-NNN head|status|export|diff|show FILE --attempt N [--static]`. It takes no git arguments: cc-factory resolves the lane, its base and the attempt's copy from the order, and builds and runs the git argv itself, with no shell (`show` reads only `README.md`, `Makefile`, `package.json` or `pyproject.toml` at the base commit; `--static` allows only head and diff). bash-guard has no exemption for verify: a `git -c core.hooksPath=…` typed into a shell is refused as always. The argv: no system or global config, `--no-optional-locks`, attributes from the empty tree, and `core.fsmonitor`, `core.hooksPath`, `core.untrackedCache`, the pager, `core.sshCommand`, every protocol and `diff.external` switched off on the command line, which outranks any config file, included ones too; diffs add `--no-ext-diff --no-textconv`. A test with a planted config shows plain git runs those programs and these commands do not. The flags cannot stop a filter driver named in `.git/info/attributes`, which `git status` and `git archive` can still reach, so verify-git runs HEAD, status, the export (`git archive` piped into `tar -x --no-same-owner --no-overwrite-dir`, extracted into the copy), the diff and the base-commit file reads only inside the sandbox; it refuses when the copy is not a directory of the user's or `bwrap` is missing.
- **No transport, no lazy fetch.** Repo config can re-enable a transport (`protocol.<name>.allow=always` outranks `protocol.allow`), and a partial-clone promisor turns a missing object into a fetch, so a planted `ext::` remote would run a program, outside the sandbox and in static mode too. Every verify git command therefore runs with `GIT_ALLOW_PROTOCOL=` (the empty list: it overrides every `protocol.*.allow` setting and allows no transport at all), `GIT_PROTOCOL_FROM_USER=0`, `GIT_NO_LAZY_FETCH=1` (honoured from git 2.44) and `-c protocol.<name>.allow=never` for ext, file, ssh, git, http and https. A missing object makes the command fail; it is never fetched, and verify reports `git: objects-missing`, which makes its verdicts static (`needs-human-check`, never `merge`). `-c extensions.partialClone=` is accepted by git but does not stop the lazy fetch (checked on 2.43), so it is not relied on. A test plants exactly that lane (an `ext::` promisor, the transport re-enabled, a blob deleted): plain git runs the program, none of verify's commands do, and those that need the blob fail closed.
- Without a sandbox (static mode), verify runs no git command outside one except `verify-git head --static` and `verify-git diff --static` (a commit-to-commit diff from the objects already present). That verify uses these exact commands is a prompt instruction.
- Verify reports the lane worktree's HEAD and `git status --porcelain` before it made the copy and after it deleted it (without a sandbox, only HEAD: its status reads `not-run`). The script compares them: a change, a missing report, or an undeleted copy ends the run `blocked` with reason `lane-tampered` and recommendation `reject`, and no further build attempt starts. The one exception: when verify reports `git` failed (or `objects-missing`), ran no lane code and gave no lane report, nothing shows the lane changed, so the run ends `blocked` with reason `infra` and recommendation `rerun` instead. A real HEAD or status change, or an unconfirmed copy removal after a run that executed lane code, stays `lane-tampered`. Either way the merge gate never opens.
- Verify also reports whether it ran lane code through the wrapper (`executed`), how the wrapper's probe went (`sandbox`: `ok`, `missing` when there is no `bwrap`, `failed` when the probe did not exit 0), and on each scenario whether it was judged by reading the code (`static`). Without a working sandbox it runs no lane code and judges every scenario by reading it. **With one, editable installs run the lane's code:** they name the main checkout by absolute path, a uv workspace member or a sub-directory package included, and inside the lane-code wrapper that path is the copy. A local package installed by value (`pip install ./pkg`, `uv sync --no-editable`) keeps main's code in the venv, which no mount can replace, so a script-built installed-copy check names such packages and verify runs no Python lane code then. Static verdicts can still fail an attempt, but the script never recommends `merge` when any scenario is static, or when `executed` is false: the merge gate gets `needs-human-check`. That the check is run and acted on is a prompt instruction. A result without these fields counts as static.
- A station whose agent returns nothing (an API error after retries, or a skip) ends the run `blocked` with reason infra and recommendation `rerun`, and the attempt is not counted.
- **A build that reports a needed deletion stops the line.** bash-guard asks a human for every `rm` outside the scratch roots and every `git rm` that deletes from the working tree, and a lane at `<project>/.claude/worktrees/` is outside them, so nobody answers the ask in a line run. `git rm --cached` only unstages, so it goes through without an ask, whatever global options come first; the lane rules forbid it all the same, since merging the lane deletes the file on master. When a build's open questions include one that starts with `needs a human deletion: <path>`, the script ends the run `blocked` with reason `needs-deletion` and recommendation `rerun`, naming the paths, and starts no rework attempt. You check the removal, `git -C <lane> rm -- <path>` and commit it in the lane yourself, then `/factory run ID` continues from there. Only that stop is code; the rules around it are asked (below).
- `record` notes (`flag: "holdout-leak"`) any 5-word overlap between the rework text build got and a scenario file, naming the attempt, station and S-id counts, never the text. It flags; it does not stop anything.

Only asked of the model, not enforced: that build, test, review and plan never read `.factory-holdout/` (no hook stops them); that stations are read-only where they should be; that no station merges or pushes; that a station stays in its lane (write-guard treats every worktree as the project); that no station deletes a file or works around the deletion ask (bash-guard does not block a removal through python or node, such as `os.remove` or `fs.unlinkSync`, or a truncating Write); that a build which needs a file removed reports `needs a human deletion: <path>` instead of leaving the file unmentioned; and that plan, build, test and review run Node tools as `npm test`, `npm run <script>` or `npx --no-install <bin>`, never a bare `npx <bin>` (the lane has no `node_modules` of its own, npm finds the main checkout's through the lane's parent directories, but bash-guard's npx lookup stops at the lane's `.git` file and asks a human), and never install dependencies in the lane. Every station verdict, "tests passed" included, is a model's report: no code runs the tests or reads an exit code. Review's own test re-run is also a model's report.

**What the sandbox does not cover.** It is OS-level only for lane code that verify runs through the wrapper; *that verify uses the wrapper* (and only the unchanged wrapper) is a prompt instruction, as is everything verify itself does with its own Bash tool. A hook that binds Bash calls from agents labelled `FO-NNN:verify` to the wrapper is on the roadmap with #10. On macOS, or anywhere without bubblewrap, there is no sandbox: verify runs no lane code and the merge gate gets `needs-human-check`. Inside the sandbox, lane code still sees the scenario inputs verify hands it and can shape its output to them within one run; it cannot store them past the run (the copy is deleted, nothing else is writable, there is no network), but scenario-specific rework feedback is still the main way a hidden check becomes a visible one. The structural fix for that is the two-tier holdout on the roadmap (#10d below): a final set of scenarios judged only on the last attempt, which never produces feedback.

**The same-user limit.** The process rules and the code stop an agent's tool calls: a Bash command runs under Claude Code, and piping an answer in, or typing one blind, does not match a code shown only on the terminal. They cannot stop a deliberately evasive process running as you that first gets past the process rules (it detaches from Claude Code, double-forks and scrubs its environment, as control mode's limit describes) and then drives a pseudo-terminal of its own, where it can read the code and type it back. Such a process can also append to the ledger with a shell (write-guard exempts `.git/cc_tool`), write a saved run file of its own under `~/.claude/projects/`, or run a modified copy of the CLI. The dashboard path adds three things in the same class. A process that rewrites its own argv and environment to pass as cc-dash, or that edits `bin/cc-factory`, is not closed. Neither needs the dashboard, and passing as cc-dash is no harder than the terminal path, only different: it takes no code typed back, but a parent running the recorded interpreter with its argv reading as `cc-dash --control`, on a terminal one of your recorded programs holds, and holding the socket alone. And an agent that drives your real browser (Claude in Chrome) can type `approve` into a tab where you have already unlocked control mode, because the typed word is a confirmation, not a secret; only the control code is secret, and it is shown on cc-dash's terminal. Do not leave a control-mode tab unlocked while a browsing agent runs. This is the same limit control mode documents in [commands](commands.md); for an agent you do not trust, use the devcontainer. Claude Code also saves the full workflow result, per-scenario reasons included, under `~/.claude/projects/.../workflows/` and in `tasks/*.output`, where a later run's build agent could read it.

## Setup

```bash
cc-setup /path/to/project               # scaffolds the factory by default
cc-update-project /path/to/project      # adds it to a project that is already set up, and refreshes factory-line.js
cc-setup /path/to/project --no-factory  # opt out: writes .claude/no-factory
cc-setup /path/to/project --factory     # opt back in: removes the marker, then runs init
cc-factory init /path/to/project        # the scaffold alone; idempotent, present files are kept unless --force
```

`cc-factory` is a `bin/` command like the others, on your PATH after cc_tool's `install.sh`. `init` scaffolds `factory/README.md`, `factory/line.json` (the `default` and `quick` lines), `factory/order-template.md` and `factory/orders/`; appends `.factory-holdout/` and `.claude/worktrees/` to `.gitignore` (once, under one comment line, even when the file has no final newline); creates the ledger directory; and copies `factory-line.js` into the project's `.claude/workflows/`. Commit `factory/` and `.gitignore`: orders and the line are source.

**Default on.** A plain `cc-setup` or `cc-update-project` runs `init`, so a project that was on Superpowers moves to the factory the next time you update it. To keep a project on Superpowers, run `cc-update-project --no-factory` (or `cc-setup --no-factory`) once: it writes `.claude/no-factory`, and every later plain run honours the marker. `--factory` removes the marker; passing both flags is an error.

A default run skips the factory, prints one line and exits 0 when:

- the marker `.claude/no-factory` exists;
- `/proc/self/status` is unreadable (`factory skipped: its gates need Linux /proc; this project stays on Superpowers`), which is macOS: the factory stays off there;
- the project is not a git work tree (`git init`, then re-run).

If `init` itself fails in a default run, setup prints a warning and carries on; under an explicit `--factory` it aborts. A skipped project has no `factory/line.json`, so the managed block's routing leaves it on the Superpowers table.

The workflow is copied because `cc-setup` and `cc-update-project` do not distribute saved workflows (cc_tool's own live only in its checkout); `init` is the one place that installs it, and the default run calls it. Re-running `init` reports the copy as up to date, refreshes one that matches an older shipped version, and keeps a locally edited copy unless `--force`. The `/factory` skill ships under `templates/skills/factory/`, so every `cc-setup` or `cc-update-project` deploys it like any other skill. A project with no copy of the workflow still works: `/factory run` falls back to `Workflow({scriptPath})` using the path in `cc-factory run-args`.

A project that already has `factory/line.json` keeps it (`init` does not overwrite a present file). The built-in `default` and `quick` lines always exist underneath it, so `quick` works there without editing the file; a line in your file replaces the built-in one of the same name.

## Orders

A work order is one file, `factory/orders/FO-NNN-<slug>.md`. **The file is the spec; the ledger is the lifecycle.** Ids are `FO-` plus a zero-padded sequence (three digits minimum), unique per repo.

```markdown
---
id: FO-003
title: Add CSV export to the reports page
priority: p2            # p1 | p2 | p3
created: 2026-10-25
line: default           # default | quick | a line of your own; fixed when the order is created
status: queued          # optional: queued or spec only; the ledger overrides it
---
## Intent
Why this exists and for whom.
## Acceptance criteria
- [ ] observable condition
## Notes
Constraints, links, prior art.
```

`cc-factory new "Add CSV export"` writes this file from `factory/order-template.md` (next free number, slug from the title; edit the template to suit the project) and a `created` ledger line. The frontmatter `status` is only where the fold starts, and only `queued` or `spec` count there: any other value (a gate status such as `approved` or `done` included) starts the order at `queued`, so an order file cannot pass a gate by saying so. The first ledger event that carries a status overrides it. The file name's slug may not contain control characters; a name that does is not an order. Reads are bounded: at most 200 orders (the highest-numbered ones) and 256 KiB per file.

**Lifecycle.** Statuses in order, then the three off the path:

| Status | Meaning |
|---|---|
| `queued` | The order exists; the spec is not finished. |
| `spec` | Spec written, waiting at the human **spec gate**. |
| `approved` | The spec gate passed; ready to run. |
| `building` | The line is running (a workflow run is in flight). |
| `verifying` | The verify station is running against the holdout scenarios. Phase 0 does not write it live: a run stays `building` until `cc-factory record` replays its stations and writes the final status, and the floor shows the live station from the workflow's agent labels. |
| `review` | After a run: every station passed on the final attempt and the order waits at the human **merge gate**, with recommendation `merge`, or `needs-scenarios` when no hidden scenario checked it. Written only by `record`; `mark` refuses it. |
| `done` | A human merged. `cc-factory` never merges; `done` is recorded by `approve --gate merge`. |
| `blocked` | Needs a human or a rerun: bad arguments, an infeasible spec, a missing environment piece, an **infra** failure (a station's agent returned nothing after an API error such as a 429, a session limit or overload, or a skipped station; this does not use up an attempt and the recommendation is `rerun`, which continues from the lane's commits, or, from the same Claude Code session only, resume the workflow run with `resumeFromRunId` to reuse finished stations), a **needs-deletion** stop (the build reported that it needs a file removed, which bash-guard asks a human for: delete it in the lane yourself, commit, and rerun), a **lane-tampered** stop (the lane worktree changed while verify ran lane code in its throwaway copy: inspect the lane and rewrite the scenarios first; verify's own git failing with no lane code run is `infra`, not this), or a `record` check that failed. Re-runnable once fixed. |
| `rejected` | A human said no, at either gate. Terminal. |
| `failed` | The line ran out of retries. Re-runnable: sharpen the spec, then `/factory run` again. |

`cc-factory list` shows `ID PRI STATUS STATION GATE LANE TITLE` and hides `done` and `rejected` unless you pass `--all`; `--json` is the same data for tooling. `cc-factory show FO-003` prints one order: status, line, rework count, gate, lane, last run id, how many holdout scenarios exist, each station's state, and the last 10 ledger events (`--events N`).

## The line

`factory/line.json` declares the stations an order passes through. A missing or broken file falls back to the built-in lines; a valid line in the file replaces the same-named built-in line, so a project can add another line (a `docs` line without the verify station, say) and point an order at it with `line: docs` or `cc-factory new ... --line docs`. Two lines ship:

| Line | Stations | Spec gate | Use it for |
|---|---|---|---|
| `default` | plan, build, test, verify (holdout), review | `human` | Anything risky: auth, payments, data migrations, security, or when unsure. 3 to 8 hidden scenarios. |
| `quick` | plan, build, test, review | `auto` | A well-understood change. At most two intake questions, no holdout scenarios, and the spec gate passes by itself, so `/factory run` follows intake without waiting for you. The merge gate is still yours. |

Models and efforts on `quick` are the same as on `default`. Because no scenario is hidden from the builder on `quick`, its tests and the review are the whole check, and the merge-gate briefing says so.

```json
{"version": 1, "lines": {"default": {"stations": [
  {"name": "plan",   "title": "Plan",   "model": "opus"},
  {"name": "build",  "title": "Build",  "model": "sonnet", "effort": "medium"},
  {"name": "test",   "title": "Test",   "model": "sonnet"},
  {"name": "verify", "title": "Verify", "model": "opus", "holdout": true},
  {"name": "review", "title": "Review", "model": "opus"}
], "gates": {"spec": "human", "merge": "human"}, "retries": 1}}}
```

A line may also set `"threshold"`, the holdout pass mark, a number above 0 and up to 1 (default 1: every scenario). It is part of what the spec gate hashes.

A line may set `"run"` and `"test"`: the commands the verify station uses to run the program and its tests (for example `"test": "make test"`). They are kept only as plain one-line strings of at most 300 characters that do not start with `-`; anything else is dropped. They are the only run instructions verify is handed, since text from the build or test station never reaches it, and they are part of what the spec gate hashes: changing one after approval needs a new approval. Without them, verify reads the repo's own README, Makefile, `package.json` or `pyproject.toml` as they were at the lane's base commit.

- **Station** = `name` (lowercase, unique, at most 12 per line), `title` (shown on the floor), `model` (an alias such as `opus` / `sonnet` / `haiku` or a full id; empty inherits the session's), optional `effort` (`low` | `medium` | `high` | `xhigh` | `max`), and `holdout: true` on the station that is handed the scenario directory. The workflow runs `plan`, `build`, `test`, `verify` and `review`, one station of each kind; a `holdout: true` station of another name is the verify kind, and `holdout: true` on plan, build, test or review is ignored. cc-factory reads the line the same way, so a station with any other name, or a second station of a kind the line already has, is dropped from the line (and from what `record` asks a pass for). A Sonnet station asked for `low` effort runs at `medium`.
- **Order of work**: plan runs once, first, and can rule the spec infeasible (the order becomes `blocked` with the reasons and a recommendation to reject or revise). Then build, test, verify and review run in line order; the first failure stops that attempt and its feedback goes to the next attempt's build. The test station reruns a failed test file once on its own, with nothing else running: a failure that passes alone is reported as `flaky` (file, first-run and rerun result lines), does not fail the station, and shows in the station note and the merge-gate briefing; a failure that fails again alone is a failure. A station whose agent returns no result (an API error after retries, or a skip) is not a failure of the work: the run is `blocked` for infra, no attempt is used, and the summary says rerun.
- **Models follow the repo's routing**: Opus plans, verifies and reviews (judgment); Sonnet builds and tests (it carries out a written spec). Review re-runs the tests itself, reports the output it observed, and fails if they do not pass, so the binding pass/fail judgement runs on Opus on the default line (the review passes only if it ran the tests and they passed). If a line gives build and review the same model family, the workflow switches review to the other one and logs it. From attempt 3 (so only with `retries` of 2 or more) a build station that is not on Opus runs on Opus, and review stays on Opus too, so on those attempts build and review share a family. The test station's prompt carries test anti-patterns (tautological and implementation-coupled tests) adapted from mattpocock/skills `tdd`. See `## Model routing` in the managed CLAUDE.md block.
- **Retries** (0 to 3, default 1): attempts = 1 + retries. A failing build, test, verify or review sends the order back to build with that station's feedback (test and review feedback is those stations' own report; verify's is the script-built text described under Holdout scenarios); the lane keeps the earlier attempts' commits and build continues from them. When attempts run out the order is `failed`, and the summary names the station that gave up. Each fail-then-restart is one **rework** on the floor and in `show`.
- **Gates**: `spec` is `human` (default) or `auto`; with `auto`, `lane` and a run do not wait for an approval. `merge` is **always** `human`: the loader forces it, whatever the file says.
- **The line is pinned.** See [What code enforces](#what-code-enforces-and-what-is-only-asked): changing an order's `line:` or rewriting its line in `factory/line.json` after creation is refused. To use another line, reject the order and file a new one.

## The plan document

The plan station's plan is also written into the lane as a Markdown file, so the Work view in cc-dash can show progress while the lane is live. `cc-factory run-args` adds two args, `planDoc` and `orderPath`, and on attempt 1 only the build station is told to write the plan verbatim to `docs/superpowers/plans/<created>-fo-nnn-<slug>.md` in the lane (`<created>` is the order's `created` date, the slug is the order file's), commit it first as `FO-NNN: plan`, and tick each `- [ ]` box as it finishes that step. The file has a `**Spec:** factory/orders/FO-NNN-<slug>.md` header and one `### Task N:` heading with one checkbox per step, the format `plans.py` already reads. On a rework build only ticks boxes. If git ignores that path the file stays uncommitted, and build says so. Review is told the plan file is not an unrelated change. An order file with no slug gets no plan document. The order file itself is never ticked: `approve` hashes it, so a tick would void the spec gate.

## Lanes

Each order builds in its own lane, a branch plus a git worktree, so parallel orders cannot trample each other and the main checkout stays yours.

```bash
cc-factory lane FO-003            # branch factory/FO-003-csv-export, worktree .claude/worktrees/FO-003-csv-export
cc-factory lane FO-003 --base v1  # branch from another ref (default: the main checkout's HEAD)
```

The branch is `factory/FO-NNN-<slug>`; the worktree is `<main checkout>/.claude/worktrees/FO-NNN-<slug>` (git-ignored by `init`, the same directory Claude Code uses for its own worktrees). Run it from the main checkout or from any worktree: `cc-factory` resolves to the main checkout either way. The base commit, branch and absolute worktree path are written to the ledger as a `lane` event, and the last stdout line is the worktree path. Running `lane` again reuses the lane, so a rework run builds on the same branch.

`lane` **refuses** (exit 2) until the spec gate has passed: when the line's spec gate is `human`, the order must be `approved` or later (`building`, `verifying`, `review`, `failed`, `blocked`) **and** the ledger must hold the spec gate's pass from `cc-factory approve` (a status set with `mark`, or written in the order file, does not count), and `done` and `rejected` orders always refuse. It also refuses when the commit the lane would check out tracks files under `.factory-holdout/`, and it checks that the ledger can record the lane (the exact worktree path) before git creates anything. Lane agents are told to work only inside the worktree, to commit on the lane branch with messages starting `FO-NNN:`, and never to push, merge, rebase or touch the main checkout. That is a request, not a fence: write-guard treats every worktree as the project, so nothing stops a station from writing into another lane. The project's `bash-guard.py` is the enforced boundary for protected branches (see the Permissions note in [workflows](workflows.md)).

## Holdout scenarios

The acceptance criteria in the order are visible to the builder; the *scenarios* are not. (This section is about lines with a verify station, such as `default`. The `quick` line has none: no scenarios, no `holdout` step, and `mark ID spec` does not ask for them.)

```bash
cc-factory holdout FO-003         # creates .factory-holdout/FO-003/ (mode 0700), prints its path
$EDITOR .factory-holdout/FO-003/S01-comma-in-a-cell.md   # one scenario per file: a user trajectory and its observable outcome
```

`.factory-holdout/` is git-ignored, so it is absent from every lane worktree by construction. `holdout` refuses (exit 2) when files under `.factory-holdout/` are already tracked (say so, with the `git rm -r --cached` that untracks them) or when `git check-ignore` says the path is not ignored; `lane` refuses when the lane's commit tracks any of them, `run-args` refuses when the lane's `HEAD` does, and the workflow refuses to start if the holdout directory sits inside the lane. The run hands the absolute path to the **verify** station only (the station marked `holdout: true`); plan, build, test and review are not given it, and are told never to read, list or ask about a `.factory-holdout` directory. That instruction is the only fence: no hook stops them.

**Why hide them.** An agent that can read its own acceptance tests grades its own homework: it builds to the test instead of the intent ("teaching to the test"), and a green run then says little about the software. Scenarios the builder has never seen are the closest thing to an independent check. Three rules keep that true:

- verify judges each scenario (satisfied or not, with its evidence) but does **not** compute the score; the line does, so the model cannot round its own grade up;
- **verify's feedback to build is built by the script, not written by verify**: build gets only the failing scenario ids, the spec's own acceptance-criterion text (looked up by index) and a failure category. Verify's per-scenario reasons stay in the workflow result for the human at the merge gate, and cannot reach build because the script never passes them on. Limit: feedback specific enough to act on still spends some of the holdout's independence, and the two-tier holdout (a feedback set and a final set) is not built. The other side of the trade: when the spec is silent on, or contradicts, what a scenario expects, build cannot learn the answer from this feedback, so the rework does not converge and the run fails; then you sharpen the spec. A 2026-10-26 re-run of a trap order went exactly this way: verify caught the hidden case on both attempts, and nothing wrong reached the merge gate;
- the scenario directory is git-ignored, so it is not in a lane's checkout.

`record` also flags, as a ledger note, any 5-word overlap between the rework text build got and the scenario files (words the spec itself contains do not count). The note names the attempt, station and S-ids with counts, never the text. It is a flag for you to read, not a stop.

**Satisfaction** is the fraction of scenarios verify judges satisfied. The default pass mark is all of them (the line's `threshold`); a scenario file with no verdict counts as unsatisfied; below the mark, verify fails and the order reworks. With no scenarios (no directory, or an empty one), or with 0 scenarios actually checked, verify passes **vacuously**, satisfaction is `null`, and `record` recommends `needs-scenarios`, never `merge`. On a line with verify, `cc-factory mark ID spec` refuses with fewer than 3 scenarios unless you pass `--no-holdout` (recorded on the event, and the briefing then says no hidden scenario checked the work). `record` refuses a result whose scenario count, S-ids, threshold or attempt differ from the files on disk. Satisfaction is a field on the review status event; the per-scenario reasons are only in the workflow result.

Phase 0 enforces the hiding by location (git-ignored, outside the lane, path given only to verify) and by instruction, not by a guard: a build agent determined to read `../../.factory-holdout/` could. See [Not done yet](#not-done-yet).

## Gates

Two human control points, both recorded in the ledger. `approve` and `reject` (both gates, `--rework` included) refuse with `BLOCKED: ... run it from your own terminal` when run under Claude Code: an agent's Bash tool, or a `!` command typed into Claude Code. From your terminal (Linux only for now) they show a random code and ask you to type it back. That stops an agent's tool calls; it is not a barrier against a process running as you (see [the same-user limit](#what-code-enforces-and-what-is-only-asked)).

**From the dashboard.** With `ccdash --control` (Linux only) every decision that waits for you can be made from the dashboard, for every project it lists. One rule, `factory.decisions()`, says which decisions an order allows, and the card, the POST and the buttons all follow it:

| Order | Decision on the dashboard |
|---|---|
| spec gate waiting | approve, reject |
| merge gate waiting | approve merge, send back, reject |
| `approved`, `failed` or `blocked`, spec changed since approval | re-approve the spec as it is now, or drop |
| `queued`, `approved`, `failed` or `blocked` | drop (reject at the spec gate). A `queued` order is never approved here: intake is unfinished |
| `building`, `verifying` | none. If the run died, `cc-factory mark FO-NNN failed --note "run died"` first |

Where the button is: the Work view, and on the Factory floor the order's inspector and the alerts band. Every order that needs you (a gate waiting, a spec changed since approval, `failed`, `blocked`) has a "needs you" cue on its tile, counts in "Needs you", makes its project hub show it and has an alert entry. A spec changed since approval says so ("spec changed since approval: re-approve") on the tile, the inspector and the Work view, and its card shows the whole current order body. A `failed` or `blocked` order shows `/factory run FO-NNN` with where to run it (a Claude Code session in the project's main checkout) and a Copy control, a `building` or `verifying` one the `mark ... failed` command the same way, to use only when the run is dead; the dashboard cannot start a run. With control mode off every decision shows the terminal command that makes it. Each action needed outside ccdash shows as one "Do this outside ccdash" box: what is needed and why, where to do it (a terminal or a Claude Code session, with the path), each command in order with a Copy control, and what to do back in ccdash. The raw text of a refusal from cc-factory or the dashboard sits under a collapsed "Details", never as the main message. A refusal the dashboard can resolve itself (a stale card, a spent view id, a spec changed while reading) offers Reload and no command.

The button opens a card in the review dialog: at the spec gate (and for a re-approval or a drop) the whole order body, its hash, and the line's stations, retries, pass mark and the commands verify will run; at the merge gate the stored briefing (the same text `cc-factory show` prints), the reviewed head, and the branch and checkout it would merge into. No scenario text appears anywhere in it, since nothing in this path reads `.factory-holdout/`. Hidden or direction-changing characters in the text are shown as `⟨U+…⟩`.

To decide you must have unlocked control mode with the control code from cc-dash's terminal, and type the word `approve` or `reject` in full. **Approve merge merges.** After every check below and the typed word, cc-dash runs `git merge --no-ff <reviewed lane head>` in the project's main checkout, onto the branch its HEAD is on (the card names both), and then the cc-factory child records it. Only that sha is ever merged. It is refused, with nothing written, when the checkout has uncommitted changes to tracked files, a merge, rebase or cherry-pick in progress, a detached HEAD, a filter or merge driver in its git config (any key ending in `clean`, `smudge`, `process` or `driver` under `filter.` or `merge.`, in any subsection, includes resolved) or attributes in `.git/info/attributes`, and when the lane moved after the review or the review stored no briefing. On a conflict it runs `git merge --abort` with the same protections, leaves the checkout as it was and says so on the card. A reviewed head already merged into HEAD is only recorded. The merge itself runs with `submodule.recurse` off and attributes taken only from the empty tree (`--attr-source`), with `core.attributesFile`, system attributes and signature checks off, so no `.gitattributes` in the tree can name a filter or merge driver, whatever the config says by merge time. Every git call cc-dash makes on this path, including the checks and the `git merge --abort` after a conflict, runs with the same two protections (`--attr-source` and `-c submodule.recurse=false`), so an abort cannot run a filter added after the check either. Git has no switch that ignores `.git/info/attributes`, so a non-empty one is refused beforehand; what is left is a same-user write to `.git` that adds an `info/attributes` line and a driver between that check and the merge, inside the same-user limit below. The merge commit carries the time cc-dash took just before the merge, rounded up to the next whole second, and the merge starts no earlier than that second. The dashboard never pushes and never deletes or moves the lane. The terminal path is unchanged: you merge, `cc-factory approve --gate merge` records. If the merge succeeds but cc-factory then refuses to record it, the card says so and gives the `cc-factory approve FO-NNN --gate merge` that records it from your terminal. A merge refusal that needs you (a dirty checkout, an operation in progress, a conflict) comes as the same box with the commands to run in the main checkout.

What is enforced before anything is written (`POST /api/control/gate`): a control-scoped token with a same-origin JSON request; the typed word; Linux `/proc`; the approvals rate limit; a single-use view id issued with that card to that client for that order and gate; the order still allowing that decision (`factory.decisions()`, on the order as it is at that moment); and the spec hash or reviewed head you were shown equal to what is there now, so a spec edited or a lane moved since is refused. Only then cc-dash mints a ticket, kept in its memory for 30 seconds, and starts `bin/cc-factory` with a fixed argv, an allowlisted environment (no `CLAUDE*`, `PYTHON*` or `LD_*`) and a socketpair on `--ticket-fd`. As above, the child checks with the kernel that its parent is a trusted cc-dash before it accepts the ticket, spends the ticket on first use, and recomputes the value before it writes. The gate event then carries `via: "dashboard"` and the `ticket` id; `cc-factory show` prints `via=dashboard`. `bin/cc-factory` stays the only ledger writer. Every attempt, refused ones included, is a `gate` line in cc-dash's `audit.jsonl`.

Any terminal works, in any directory, for every project the dashboard lists, with no recording step: the terminal showing the control code is checked live (the rules `cc-dash --record-code` and `cc-update-project` record by: not inside Claude Code, a pseudo-terminal of its own, no detached terminal driver, no fresh session after a re-parent, and a holder of the terminal that is no generic interpreter, terminal driver or copy of one). That is weaker than the recorded list: a non-interpreter terminal program (tmux, an xterm) that an agent starts with a scrubbed environment, detached from Claude Code, now passes where an unrecorded program used to be refused. It is inside the same-user limit below. A project still needs `cc-update-project` once for its pin (the checkout it was set up from).

**One code record for every project.** The code you approved is recorded once per user, in `${XDG_STATE_HOME:-~/.local/state}/cc_tool/cc_dash_code.json` (0600, your own plain file, no symlink; the same rules the per-project manifest was read by): the sha256 of every cc-dash code file, the interpreter, keyed by checkout. The control hook, cc-factory and cc-dash all read that one file, so updating cc_tool needs one re-record for all projects, not one per project. It changes in two ways only:

- **From your terminal:** `cc-dash --record-code` records this checkout's code (`cc-setup` and `cc-update-project` do it too when run from a terminal). All three refuse under Claude Code, by the rules `cc-dash --control` starts by. Then restart `ccdash --control`.
- **By a dashboard merge you approved.** When Approve merge merges a reviewed lane into the cc_tool checkout itself, cc-factory (inside the same ticketed `approve --gate merge` that records the merge) re-records exactly the files the merge brought in unchanged from the reviewed commit: HEAD must be a two-parent merge of exactly the reviewed head, HEAD's tree must equal a clean `git merge-tree --write-tree` of its two parents, and a file counts only when the lane changed it (it differs between the merge-base and the reviewed commit), its content equals the reviewed commit's and the record held its content before the merge. Changes the merge made are exempt from the dashboard's change-time check only from the merge commit's time on (that rounded-up timestamp, never earlier than the moment cc-dash took it): anything changed earlier, after the dashboard started, is still refused. The dashboard then says it must restart and offers a Restart button (control mode): it starts a fresh cc-dash in the same terminal, as its own process-group leader like a dashboard started directly, and the new one decides again with no command typed (you unlock it with the code it shows). A hand edit, a `git pull`, an evil merge or an agent's write is never in that delta.

Code that differs from the record for any other reason shows one "Do this outside ccdash" box on the gate card before a decision is attempted, with one command (`cc-dash --record-code`) plus the restart, never a per-project list; a decision is refused with that box and writes nothing. A per-project `cc_dash_manifest.json` still carries the other fields, but its code record is no longer judged. A project's hook copy from before this change keeps reading the per-project manifest until its next `cc-update-project`.

**Why this is no weakening.** Only code a human approved is trusted: recorded from their terminal, or the exact tree they merged through a gate decision. An agent that edits cc-dash's code with Bash leaves the disk different from the record, so every decision is refused, whether the dashboard restarts or not; writing the record is denied where the hooks can see it (write-guard denies Edit and Write on it; bash-guard, a rule that matches names and is not a boundary, see below, denies any command that names it unless the command only reads it (`ls`, `stat`, `cat`, `head`, `tail`, `wc`, `file`, `grep`/`rg`, `jq`, `git log`/`show`/`diff`/`grep`, with no output redirect or `tee`) or names it in a `git commit` message, and denies `--record-code` beside a `cc-dash`/`ccdash` token however it is started or beside a program word it cannot read (`$(…)`, a backtick, a `$` variable); and the recorders refuse under Claude Code); and a ticket needs a dashboard that passes the code check.

**What the code-record rule covers in bash-guard.** A command substitution is never a read: its body is found by a scanner that tracks single quotes, double quotes and backslashes (a substitution inside real single quotes is text) and is matched for the record name and for `--record-code` after its quotes and backslashes are removed, so `cc_dash_code''.json` and `--record""-code` are seen; when the scanner cannot finish (an unbalanced quote, an unclosed substitution) the whole command is scanned that way. A pipeline with `xargs`, `parallel` or a runner reading code from stdin is denied when its text holds `--record-code` beside a `cc-dash`/`ccdash` token or a word bash-guard cannot read. A word or redirect target in a command that does not only read whose basename can match `cc_dash_code.json` once globs and run-time parts (`$name`, `${…}`, `$(…)`, a backtick, `{…}`) count as wildcards is denied when it sits in cc_tool's state directory (written with `~`, `$HOME` or `$XDG_STATE_HOME`) or the basename holds `cc_dash`; so is a command that is not a read and names the state directory itself (`rm -rf ~/.local/state/cc_tool`); the state directory is compared after `//`, `/./` and a trailing `/.` are normalized. A raw-text backstop runs first, on the command with its quotes and backslashes removed and `//` and `/./` collapsed: when that text names the record or a pattern for it, the state directory, or `--record-code` beside a `cc-dash` token or a `$`, and it also holds a `$`, a backtick, a process substitution or (for a name) a glob, the command is denied unless it holds no substitution and is only allowlisted reads, `cd`, `pwd`, `true` or `test`. Single-quoted text and an escaped `$` or backtick count as text only when every command in the line prints or reads its arguments (the readers, `cd`, `pwd`, `true`, `test`, `echo`, `printf`, `git commit`) and the line has no substitution; with any other command (`ssh`, `flock -c`, `find -exec`, `su -c`) they stay live. `--record-code` beside a `cc-dash` token needs nothing dynamic: it is denied unless every command in the line is on that list. `xargs` or `parallel` running `cc-dash` is denied whatever feeds it. This rule matches names and is not a boundary: a name built where bash-guard cannot see it (a relative write after `cd` into the state directory, a script given by path, a copy of a whole directory tree from elsewhere) is outside it and falls under [the same-user limit](#what-code-enforces-and-what-is-only-asked), as does a raw write by a process that is no tool call of an agent.

**IDE terminals.** `ccdash --control` starts and decides in a Cursor or VS Code terminal while Claude Code runs in other tabs: a holder of the terminal's master that vanishes during the scan (an IDE's `cpuUsage.sh`, `sed`, `sleep`) triggers one bounded rescan, and is ignored only once confirmed gone; one that vanishes again on the rescan is never assumed gone, and the check refuses ("kept changing; try again"). The scans for a hidden holder list /proc once more when an unreadable process exits during the settle, so a child it forked meanwhile is judged too; a newcomer that cannot be read counts as hidden, and the check then runs one fresh scan and refuses if anything is hidden in it. A `claude` process that holds the master passes only when it inherited it from the terminal host, every master descriptor it has carries `O_CLOEXEC`, and `kernel.yama.ptrace_scope` is 1 or more: no tool call of that claude inherits the descriptor, and a descendant cannot ptrace it or `pidfd_getfd` it away. A descendant of claude holding the master, a claude without `O_CLOEXEC` and a system without Yama still refuse, each with one plain sentence on what to do (start it in a terminal outside the IDE).

**Not closed:** bash-guard's code-record rule matches names and is not a boundary (a name built where it cannot see it is outside it, see above); an agent that drives your real browser can type the word into an unlocked tab; a process that fakes cc-dash's argv and environment, edits `bin/cc-factory`, or appends to the ledger with a shell is not stopped either. See [the same-user limit](#what-code-enforces-and-what-is-only-asked).

- **Spec gate** (`spec` to `approved`). You read the spec the interview produced and either pass it or send it away. The spec becomes every station's prompt, and the line's agents edit and commit in `acceptEdits`, so this read is also the check against instructions planted in a GitHub issue the order came from. Approving stores a hash of the order body, the line and the threshold: edit any of them afterwards and `run-args` and `record` refuse until you approve again.

  ```bash
  cc-factory approve FO-003 --note "scope is right"      # status approved; the line may run
  cc-factory reject  FO-003 --note "too broad, split"    # status rejected
  ```
- **Merge gate** (`review` to `done`). `record` prints the briefing from facts, beginning with a `Line:` row naming the line the order ran on: `git diff --stat base...branch` and `git log --oneline base..branch` from the lane; satisfaction and the S-ids; review's verdict, summary, every should-fix item and its full next steps; and review's own test re-run. Review's summary, should-fix items and next steps print whole; the commit and diffstat lists stop at 30 and 40 lines ("... N more"). The terminal gets the whole briefing; the ledger keeps it redacted and capped at 12000 characters on the review event, and `cc-factory show ID` prints it again. At the merge gate the recommendation is `merge`, `needs-scenarios` (a line with verify, but no hidden scenario was checked; a line with no verify station recommends `merge` and the briefing says it has no hidden scenarios by design) or `needs-human-check` (verify could not run the lane's code in the sandbox and judged by reading it); a run that did not reach it recommends `rework` (failed), `reject` (the plan judged the spec infeasible) or `rerun` (infra). A recommendation is advice, and the station verdicts in it are model reports. **You** merge the reviewed commit yourself, locally or through a pull request; `cc-factory` never touches your branches. Merge the sha `record` printed, not the branch name: a branch that moved after the review is refused at the gate. The gate needs that exact commit in `HEAD`, so use a merge commit. A squash or rebase merge rewrites the commit and is refused; after a squash, `git merge --no-ff <sha>` on top of it still passes, where the branch allows that. Work that lands through an integration branch passes with `cc-factory approve ID --gate merge --into <branch>` in your terminal (the dashboard has no `--into`). If none of these fit, the way out is `cc-factory reject`.

  ```bash
  git merge --no-ff 3f9c2e1d…                           # the reviewed lane head record printed; your call, your tooling
  cc-factory approve FO-003 --gate merge                 # asks you to type back a code it shows; checks exactly the reviewed head is merged into HEAD, records the merge sha: status done
  cc-factory reject  FO-003 --gate merge --rework --note "export ignores filters"   # back to approved; the lane is reused
  cc-factory reject  FO-003 --gate merge                 # not merging: status rejected
  ```

Without `--gate`, the gate is the merge gate when the order is in `review` and the spec gate otherwise; `--rework` applies to the merge gate only; a finished (`done` or `rejected`) order takes neither. `approved` and `done` are written only by `approve`: `cc-factory mark` refuses them (and `review`, which only `record` writes), an order file's frontmatter cannot set them, and `lane` and `run-args` look for the spec gate's pass event itself, not just the status. The recommendation is advice: nothing in the line merges, pushes or opens a pull request.

## The ledger

`<git common dir>/cc_tool/factory/ledger.jsonl`, for a normal checkout `.git/cc_tool/factory/ledger.jsonl`. The git common dir is shared by the main checkout and every linked worktree, so a lane and the main checkout write and read **one** ledger. It is append-only and written only by `cc-factory`; cc-dash and the skill only read it. One JSON object per line:

```json
{"t": 1761400000.12, "order": "FO-003", "event": "status", "status": "building",
 "station": "build", "state": "start", "run_id": "wf_ab12cd",
 "branch": "factory/FO-003-csv-export", "worktree": "/abs/path", "note": "", "by": "cc-factory"}
```

`event` is `created`, `status`, `station`, `gate`, `lane` or `note`; `state` is `start`, `pass`, `fail` or `waiting`; gate events carry `gate: spec|merge`; `lane` events carry the lane's `base` commit. A gate event decided from the dashboard also carries `via: "dashboard"` and `ticket` (the single-use ticket's id); a decision from a terminal has neither. `run_id` and `branch` are single lines; `worktree` is a path, kept with its spaces, without control characters, at most 1024 characters. Readers ignore unknown keys and skip lines that do not parse, so the format can grow. An order's current status, station, gate and rework count are not stored anywhere: they are **folded** from these events (plus the order file) every time, so there is no second source of truth to drift.

**Safety.** The ledger directory is created `0700` and the file `0600`; `cc-factory` refuses a ledger that is a symlink, has more than one link, or is not owned by you, and readers apply the same ownership rule. Notes are clipped to 500 characters and redacted for secret shapes (API keys, tokens, private keys, `password=...` pairs) before they are written, and order text is never copied into the ledger. **Never put secrets in a note, an order or a scenario.** Reads are bounded (the last 4 MiB of the ledger).

## The /factory skill

The `factory` project skill is the conversational front for `cc-factory`: it asks, writes and runs; the script records. Four operations:

| Operation | What it does |
|---|---|
| `/factory intake` | Takes your idea or a GitHub issue (`gh issue view`), first picks the line (`default` or `quick`) and says which in chat. Then asks three to five questions (at most two on `quick`: who it is for, what observable result means done, what is out of scope), creates the order with `cc-factory new --line`, fills Intent / Acceptance criteria / Notes, and on `default` writes 3 to 8 holdout scenarios as `S01-<slug>.md`, marks the order `spec`, and shows you the order file (not the scenarios). It tells you to run `cc-factory approve` in your own terminal; it cannot (the command refuses under Claude Code), and it is told not to try a workaround. `mark spec` needs 3 scenarios unless `--no-holdout`. On `quick` there are no scenarios and the spec gate is automatic, so intake goes straight on to `run`. |
| `/factory run ID` | Needs status `approved` (or `failed` / `blocked` for a rerun, or `queued` / `spec` on a line whose spec gate is `auto`). Makes or reuses the lane, reads `cc-factory run-args`, marks `building`, launches the `factory-line` workflow (`Workflow({name})`, or `Workflow({scriptPath})` when the project has no copy; it runs in the background and the session waits for its notification), checks the run picked up its args, then runs `cc-factory record ID --workflow-run <runId>`, which reads the result Claude Code saved (no heredoc, no piping, and never through a file in the scratchpad, which the line's agents share), failed and blocked runs included. It ends with the briefing `record` printed and the commands for you to run; on `blocked` for infra it says rerun, or resume with `resumeFromRunId` from the same session, on `needs-scenarios` that no hidden scenario checked the change. |
| `/factory status` | `cc-factory list`, or `show ID` for one order: stations, gate, lane, run id, recent events. |
| `/factory gate` | Finds the orders whose gate is waiting. At the spec gate it shows the order and asks approve or reject; at the merge gate it gives the review summary, the lane's `git diff --stat` and the merge commands. It records exactly the decision you make, never one for you. |

Six invariants hold in every operation. They are instructions to the model, except where the CLI refuses on its own (the gate commands under Claude Code, `mark`, `lane`, `run-args`, `record`): the CLI owns the lifecycle (the skill never edits the ledger or writes a status into an order file); the holdout stays hidden (scenario text never goes into the order file, a plan, an agent prompt, a commit message or a chat summary, and scenarios are referred to by count and S-number only); humans merge (the skill never merges, pushes, rebases or deletes a lane unless you ask in that turn); the plan station does the planning (the skill never invokes `superpowers:writing-plans` or `superpowers:subagent-driven-development` for an order); an order's line is fixed at creation (the skill never changes it afterwards); and a `BLOCKED:` refusal is relayed with its suggestion, never worked around. In a project with no `factory/line.json` the skill says there is no factory and carries on with Superpowers.


If a station fails an attempt, the order reworks inside the same run (once, by default) before it ever reaches you; on a second failure it is `failed`, and `show` has the station and the reason.

## The floor (cc-dash)

cc-dash shows the factory on its **Factory** tab (`#/factory`, key `f`), the landing view: one live graph of projects, sessions, agents, workflows and **orders**, wired by who spawned whom. A project is a disc ringed by its model mix; every other node's face carries its model, state, current tool, how long it has been in that state (from a minute in), cost and burn, and an order's also its station stepper and, once it has been sent back, its rework count; particles flow down the edges at the rate of token burn. Zoomed out to where a busy floor fits, a failed node keeps a red ring, a stalled one a dashed amber ring and anything that needs you a wider amber halo, so they can be found among hundreds. An order node sits beside its project and is linked to its workflow runs by the ledger `run_id` and by the agent labels the workflow sets (`FO-003:build`, with the station title as the phase), and to any session working on its lane branch. An order waiting at a gate is marked as needing you in amber, like an agent waiting on a prompt.

- **Instrument panel**, across the top of the stage: the totals, what needs you, your subscription's 5-hour and weekly **usage limits** (use, and time to reset; recorded by `cc-statusline`, see [commands.md](commands.md)), and the **Activity** toggle.
- **Activity column**, on the right: **Recent actions**, the 8 newest tool calls on the floor (when, which agent in its model's colour, the tool and its target, running, ok, failed or blocked), newest first; a row shows its node, and the list holds still while your pointer or focus is on it. Under it, **Last hour**: new tokens (by model family), tool calls (the failed ones in red) and working agents, each in 20 bars of 3 minutes headed by the hour's total (for agents, the peak), always the last 60 minutes whatever the window picker says; the lighter last bar is the 3 minutes still running. Hover a bar, or focus a chart and use the arrow keys, for its exact figures. On a short window the list shows fewer rows (the next one peeks out, the rest scroll) so the charts keep their height. It is shown by default on a window wider than 900 px; narrower, the Activity toggle opens it (a bottom sheet on a phone), and the toggle hides it anywhere.
- **Inspector**: selecting a node (click, or the arrow keys and Enter) opens it in the column's place (a bottom sheet on a phone), and closing it brings the column back; the two share one slot of one width, so a pick never re-fits the floor. An order shows its stations, gate, lane and rework count; a session or agent shows its activity, tokens and guard catches; a session or agent links to its session or agent page, and a project or order to its project's Overview and Work (an order's Work link opens that order's row, `#/plans?p=<project>&order=FO-NNN`, and its Spec row opens the order file in Docs). The floor re-frames so the node, its parent and its children stay clear of the panel. Double-click opens a node's page.
- **Camera and scope**: `+`, `-` and `0` zoom and fit (the fit keeps nodes out from under the column, the inspector and the zoom buttons). Alert toasts sit to the left of the zoom buttons, and of the column or an open inspector, and never move the camera; on a phone they sit above the zoom row and step aside while the inspector's bottom sheet is up (the alert strip still lists what needs you). The project picker narrows the floor to one project, and **Dormant projects** adds the projects with no live session or open order.
- **List** shows the same tree as a list of buttons: the keyboard and screen-reader path, and the fallback when the graph engine cannot start. Reduced motion stops the flow and the breathing.

The floor passes no gates: it marks an order that needs you, and the gate buttons are on the Work view (see [Gates](#gates)). Without control mode, approvals go through the CLI (or the skill). With `cc-dash --control`, a session or agent waiting on a decision (a permission, a question or a plan) gets a **Review** button (**Answer** for a question, **Review plan** for a plan), in the alert strip and in its inspector. It opens the full decision card in a dialog over the floor, the same card as the toasts and the session page; the strip and the inspector only summarize the request in one line, and a decision is made on the card alone. Escape closes the dialog. Without control mode (a plain read-only pairing) there is no Review; until you type the control code, the card asks for it, as everywhere. Projects (Overview, Sessions, Work, Docs) and the session and agent pages are the drill-downs from the floor; the old Live tab is gone, and `#/live` redirects here.

**The Work view** (the Projects tab that used to read Plans; `#/plans`, key `p`) is where an order's paper trail is. Its sections, each with a count and left out when empty: **Orders** (id, title, status, the same station stepper as the floor, the line, the plan and the lane branch), **Plans**, **Documents** and **Agent runs**. `?order=FO-NNN` scrolls to and highlights an order. An order waiting at a gate shows the terminal commands that pass or reject it (`cc-factory approve FO-NNN --gate merge` and `reject`); in control mode it shows a **Review spec gate** or **Review merge gate** button instead (see [Gates](#gates)). A plan card links to its spec and to the order it belongs to, joined by the plan's `**Spec:**` line, including a plan written inside a live lane under `.claude/worktrees/`. Order progress is the number of passed stations, never checkboxes. See [commands](commands.md) for the full page.

## CLI reference

| Command | What it does |
|---|---|
| `cc-factory init [PROJECT] [--force]` | Scaffold `factory/`, the `.gitignore` lines, the ledger dir and `factory-line.js`. `cc-setup` and `cc-update-project` run it by default. |
| `cc-factory new TITLE... [--priority p1\|p2\|p3] [--line NAME]` | Create an order file and its `created` event, which pins the line's name and a hash of its definition. |
| `cc-factory list [--all] [--json]` | The board (alias `status`); hides `done` / `rejected` without `--all`. |
| `cc-factory show ID [--json] [--events N]` | One order, folded from the ledger, with the last merge-gate briefing. |
| `cc-factory mark ID [STATUS] [--station S --state start\|pass\|fail\|waiting] [--run-id R] [--branch B] [--worktree W] [--note TEXT] [--no-holdout]` | Append a status, station or note event. Not `approved`, `done` or `review`: gate decisions are made with `approve`, and `review` is written by `record`. `mark ID spec` refuses with fewer than 3 scenarios unless `--no-holdout`. |
| `cc-factory approve ID [--gate spec\|merge] [--note TEXT] [--into REF]` | Pass a gate: spec makes `approved` and stores the spec hash; merge makes `done` (exactly the reviewed lane head must be merged into `--into REF`, default the main checkout's HEAD, the branch unmoved since the review; records the merge sha). Refuses under Claude Code and without `/proc` (Linux only for now): run it in your own terminal, where it shows a random code to type back. |
| `cc-factory reject ID [--gate spec\|merge] [--rework] [--note TEXT]` | Fail a gate: `rejected`, or at the merge gate with `--rework`, back to `approved`. Refuses under Claude Code and without `/proc`, and asks for the code, like `approve`. |
| `cc-factory lane ID [--base REF] [--json]` | Create (or reuse) the branch and worktree; the last stdout line is the worktree path. Refuses when the order's line no longer matches its pin. |
| `cc-factory holdout ID` | Create the git-ignored scenario directory; the last stdout line is its path. |
| `cc-factory run-args ID` | JSON for the `Workflow` tool: `{name, scriptPath, args}`. Includes the line's `threshold` and, for an order whose file has a slug, `planDoc` and `orderPath` (see [the plan document](#the-plan-document)), and `subPackages`, the top-level sub-directories with their own `.venv` or `node_modules` for the verify sandbox (`[]` when none). Refuses when the order's line no longer matches its pin, without a recorded lane, without the spec gate's pass (on a `human` spec gate), when the spec changed since approval, and when the lane's `HEAD` tracks files under `.factory-holdout/`. |
| `cc-factory verify-git ID head\|status\|export\|diff\|show FILE --attempt N [--static]` | The verify station's only git, on the order's lane: a fixed, hardened argv run inside the attempt's bwrap sandbox (`--static`: head or diff without one), no git arguments accepted. See [What code enforces](#what-code-enforces-and-what-is-only-asked) for what it switches off. |
| `cc-factory record ID [--workflow-run RUNID] [--run-id R] [--file F]` | Write a workflow result into the ledger: one station event per history entry, then the final status, and print the merge-gate briefing. `--workflow-run` reads the result Claude Code saved under `~/.claude/projects/<project>/<session>/workflows/<runId>.json`; its args must match the order and line. `--file` and stdin also work, but only for `failed` or `blocked`. Writes `review` only for a `--workflow-run` result with `contract: 2` in which every station passed on the final attempt and the verify result matches the scenario files on disk; otherwise records `blocked` and exits 2. |

`-C DIR` before or after the subcommand points it at another project (default: the current directory; it resolves to the nearest `.git`, then to the main checkout). IDs are forgiving: `3`, `fo-3` and `FO-003` are the same order. Machine output (`list --json`, `show --json`, `lane --json`, `run-args`) is ASCII-only JSON, and paths in refusals are printed without control characters. Exit codes: `0` ok, `1` usage or unknown id, `2` refused, with `BLOCKED: <reason>. Suggestion: <what to do>.` on stderr.

## Not done yet

The factory is an experiment: the core, the line and the floor work, and the gaps below are known and open. Numbers follow the prioritized gap list of an independent assessment made on 2026-10-25 (not part of this repository). Gaps 0 to 7 are addressed in this release, except one part of #4: a rerun still starts without the last run's failure feedback.

- **macOS factory gates** via a sysctl/`ps` lineage check: today `approve` and `reject` refuse without `/proc`.
- **#8 Prompts fight the permission system**: lane rules use `cd <dir> && cmd`, which a project allowlist can refuse, and a headless run on an untrusted workspace ignores the project allowlist. A build may not delete a file either (bash-guard asks for every `rm` and `git rm` in a lane): the run stops `blocked` (`needs-deletion`) for a human to do it, where a fixed `cc-factory` subcommand that runs `git rm` inside the order's own lane could let the line finish.
- **#9 No deterministic checks**: a `cc-factory check` (run the tests at lane HEAD, fail-first on new tests, no deleted tests or new skips) so a pass does not rest on a model's report.
- **#10 The holdout is not enforced**: scenarios out of the project tree, a hook that denies the path to every station but verify, a hook that binds verify's Bash calls to the sandbox wrapper, hashing at the spec gate, and (#10d) the two-tier holdout, whose final tier never produces feedback.
- **#11 No docs station**: nothing updates docs or the changelog for a user-visible change.
- **#12 Thin ledger, no metrics**: station events carry the record time, not their own, and there are no model, effort, cost or approver fields (satisfaction and the merge sha are recorded), and no lead time, first-pass yield or rework rate.
- **#13 Untrusted intake**: a GitHub issue still reaches the main session as raw text.
- **#14 The merge path and lanes are only partly guarded**: bash-guard asks before a merge, rebase, pull or reset into a protected branch and before a non-read git command that names one, but it is a text guard with a documented residual class (a `cd` into another repository, `.git/config` edited by hand through the shell). The structural fix is a git `reference-transaction` hook that refuses agent-originated updates to protected refs, whatever command made them. Nothing stops a push of `factory/*`, a write into another lane, or an append to the ledger.
- **#15 No cost cap** per order.
- **#16 No dispatcher** between orders (WIP limit, merge queue).
- **#17 No kaizen loop** from failures back into scenarios, rules and line config.
- **#18 The verifier is never calibrated** against the human's merge decisions.
- **#19 No realistic environments** beyond CLIs and libraries.
- **Non-goals**: a daemon, an MCP server, auto-merge to protected branches, a cloud dependency.

**Headless runs time out.** Observed on Claude Code 2.1.309, not a documented limit: in a `claude -p` session the turn ends while the line keeps running in the background, and the Workflow is then aborted. A real line run was killed at about 610 seconds (status `killed`, error `Workflow aborted`), and the session never got the completion notice, so `record` did not run. `cc-factory record` refuses a killed run, correctly. An interactive session is not affected, and neither is a headless session held open with `--input-format stream-json` and stdin left open: a 673-second line ran to completion that way and recorded its own result. A line that takes longer than about 10 minutes needs one of those two. After a kill the order is still `building`; run `cc-factory mark ID failed`, then `/factory run ID`, which continues from the lane's commits.

A line run is an ordinary `Workflow`, so it has the same constraints as any unattended workflow: no one answers a permission prompt mid-run. Read [Dynamic workflows & unattended runs](workflows.md#unattended--autonomous-runs) and [Sandboxing](sandboxing.md) before you schedule one.
