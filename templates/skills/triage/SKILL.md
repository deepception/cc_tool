# Triage

Clears an inbound issue backlog into a state a human or an agent can act on, without silently mutating a shared tracker. Nothing gets labeled, commented, or closed without a confirmed recommendation first.

## Scope

External, untriaged issues only: bug reports, feature requests, unsolicited PRs. Skip issues already past `needs-triage` unless the user asks to revisit one, and skip issues the user filed themself — their own planned work goes through `superpowers:brainstorming` → `:writing-plans`, not this skill.

## Label schema

- Category (exactly one): `bug`, `enhancement`
- State (exactly one): `needs-triage` (default) → `needs-info` | `ready-for-agent` | `ready-for-human` | `wontfix`

## Workflow

### 1. Bootstrap (first run in a repo)

Run `gh label list` and compare against the 7 labels above. If any are missing, propose creating them (name, color, description) and wait for confirmation before running `gh label create`. Never create labels without confirmation.

### 2. Gather untriaged issues

`gh issue list --label needs-triage` (or, if labels aren't applied yet, every open issue not filed by the repo owner). For each:

- **Redundancy check** — already implemented, or a duplicate of an open issue?
- **Prior-rejection check** — does `.out-of-scope/*.md` already cover this concept?
- **Verify** — bug reports: attempt to reproduce from the reporter's steps (reproduced-with-code-path / failed-to-reproduce / insufficient-detail — the code path is for your own confidence here, it does not appear in the eventual comment; see the no-file-paths rule below). Unsolicited PRs: check out the branch, run the relevant tests/build, and note whether the change is already complete and correct as-is.
- Form a recommended category + state + one-line reasoning.

Do this for every untriaged issue before presenting anything — batch, not per-issue.

### 3. Present and confirm

Show one table: issue, recommended category + state, reasoning. Nothing is applied until the user confirms — labels and comments on a shared tracker are visible to others, same bar as any other consequential action.

### 4. Apply

Per issue, on confirmation:

| Target state | Action |
|---|---|
| `ready-for-agent` | Post a durable agent-brief comment: contracts, types, behavioral expectations. No file paths or line numbers — it must survive refactors between now and pickup. Point at `superpowers:writing-plans` / `:executing-plans` as the next step. |
| `ready-for-human` — needs a human call | Same brief format, plus one paragraph on why this needs a human call (design judgment, security-sensitive, ambiguous product decision). |
| `ready-for-human` — unsolicited PR, already verified correct | Skip the brief — there's no work left to describe. Post a verification summary (what you checked out, what you ran, the result) and recommend merge by a maintainer with write access. |
| `needs-info` | Comment asking the reporter for the specific missing detail; state stays `needs-info`. |
| `wontfix` — already implemented | Comment with the location, close. No `.out-of-scope/` file. |
| `wontfix` — duplicate of an open issue | Comment linking the original issue, close. No `.out-of-scope/` file. |
| `wontfix` — rejected bug | Polite explanation, close. |
| `wontfix` — rejected enhancement, no prior record | Write `.out-of-scope/<slug>.md` (concept, reasoning, linked issue), close. |
| `wontfix` — rejected enhancement, matches an existing `.out-of-scope/` entry | Comment citing that file's existing reasoning and linking the new issue, close. Do not rewrite the file. |

Every AI-authored comment ends with `_This was generated by AI during triage._`

## Anti-patterns

- Applying a label or posting a comment before the batch confirmation.
- Writing file paths or line numbers into an agent brief — it's a contract, not a code pointer.
- Treating an issue the user filed themself as triage input.
- Silently creating labels on first run instead of proposing them.
